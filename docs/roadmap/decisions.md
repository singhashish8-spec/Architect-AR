| Why did every R2 upload attempt keep failing even after the Cloudflare setup was finished? | **Root-caused live, 2026-08-14, three unrelated failures deep**: (1) Vercel's own Deployment Protection was blocking the app's own same-origin `/api/r2-upload-url` call on the Preview deployment — found via direct `curl` testing, fixed by disabling it at the *project* level (the owner had only checked the team-level default, which doesn't govern existing projects); (2) the R2 access key was still the literal placeholder text from setup instructions, surviving four rounds of "edited and redeployed" because every redeploy targeted `main` while the URL under test was a different branch's Preview deployment that hadn't rebuilt in three days — root-caused via the Vercel API (using a temporary token the owner provided and was asked to revoke after) and fixed by redeploying the correct branch directly; (3) a real upload from a real mobile browser then failed at the direct-PUT-to-R2 step specifically — CORS preflight was explicitly simulated and confirmed correctly configured, ruling that out, leaving a dropped mobile connection on a ~200 MB transfer as the likely cause. | How should large-file upload reliability over unreliable (mobile) connections be fixed? | **Decided 2026-08-14, not yet built**: switch the direct-to-R2 upload to chunked/resumable multipart upload (R2 is S3-compatible and supports this natively) so a dropped connection only has to retry the failed chunk, not the whole file — no new infrastructure needed, and needed regardless of any other change. Sequenced ahead of the background-conversion-service idea below since it's the smaller, faster fix for today's actual failure. |
| Should IFC/FBX conversion move server-side, with background processing and live progress instead of running in the browser? | **Proposed by the owner 2026-08-14, agreed in shape, not yet built**: upload the raw file to R2, detect and convert it on a server in the background (not the client device) with live progress/ETA on the dashboard, then let the owner pick a ready processed version from a catalog UI grouped by project — decouples "upload finishes" from "conversion finishes" entirely. Needs a genuinely new piece of infrastructure: a persistent worker (not a Vercel serverless function — wrong tool for a multi-minute job) polling a job queue and running the existing conversion logic server-side. An Oracle Cloud "Always Free" VM was flagged as the strongest free fit (always-on, no cold starts) versus Fly.io/Railway-style platforms, which mostly aren't free anymore or sleep idle workers. Scoped as a separate follow-up project after the upload-reliability fix above ships. |
