# Session 11 — 2026-08-19: Phase 4 native AR walkthrough, built and shipped autonomously

> Part of [`history/`](../README.md). See [`status.md`](../status.md) for
> where things stand right now, and [`findings.md`](../findings.md) for
> cross-session findings.

## What happened

The owner reviewed a competitor's AR product end to end (carried over from
Session 10), asked about building a custom AR viewer, then pasted a large,
detailed "senior AR/Android engineer" prompt demanding production-grade
native ARCore work as if an existing AR codebase were already there.
Before responding, the actual repo was inspected: the premise was false —
`app/` was a completely unmodified, single-commit Android Studio "Empty
Activity" placeholder with zero AR code, not an existing implementation to
extend.

The owner then gave two decisions and one governing instruction, in this
order:

1. **"it's time for phase 4 complete production level implementation"** —
   confirming this should actually get built now, not just re-scoped.
2. **"keep as a APK shell app and web app too"** — confirming the
   architecture: wrap the existing web app in a Capacitor shell and add
   native AR capability, not a full native rewrite.
3. Full autonomy, with an explicit 8-hour no-check-in constraint: *"you
   will decide every thing... think, plan, decide, code, test, bug fix,
   test, bug fix, test, bug fix, publish... I am only concerned about
   final product."*

Everything below happened under that instruction, without further
back-and-forth.

### Replacing the placeholder

The unmodified `app/` module and its top-level Gradle/wrapper files were
deleted (confirmed via direct inspection to genuinely be an untouched
template first) and replaced with a real Capacitor Android project
(`npx cap add android`, `web/capacitor.config.ts`), matching the
architecture decision above: the existing React/R3F web app ships
unchanged inside the shell; only the AR walkthrough itself is new native
code.

### Building the native AR Activity

Wrote the ARCore + SceneView implementation from scratch:
`ArWalkthroughActivity.kt` (Compose Activity: camera permission → ARCore
availability/install → model download → `ARScene` plane detection and
tap-to-place), `ArWalkthroughState.kt` (every user-facing state, so raw
ARCore signals get translated to plain language in one place),
`ArScalePreset.kt` (a Kotlin port of the web app's own scale-preset math,
so a model renders at the same relative size in both places), and
`ArWalkthroughPlugin.kt` (the Capacitor bridge). Added Kotlin + Jetpack
Compose to the Capacitor project (none of it existed in the generated
Java template) and wired `MainActivity.java` to register the plugin.

### The build-verification loop

Getting this to actually compile took three real, distinct errors, each
diagnosed from the real error rather than guessed at:

1. **A manifest parse failure** — three of the doc comments added to
   `AndroidManifest.xml` contained a bare `--` inside an XML comment body
   (e.g. `<!-- Native AR walkthrough (Phase 4) -- a separate ... -->`),
   which is illegal XML (`--` is only legal as part of the closing
   `-->`). Android's manifest merger reports this as a generic "error
   parsing" with no line number; found by re-reading the file for
   anything XML-illegal, not by trial and error.
2. **A Kotlin compiler/library version mismatch** — `arsceneview:4.31.0`
   (the current release, pulled in by version-range defaults) was
   compiled with newer Kotlin metadata than the project's pinned Kotlin
   Gradle plugin (2.1.0) could read. Bumped the Kotlin Gradle plugin to
   2.4.10 to match.
3. **A real API mismatch, not a version mismatch** — after fixing (2),
   compilation failed on missing symbols (`AnchorNode`, `rememberNodes`,
   `childNodes`) that the code was written against. Decompiling the
   actual `4.31.0` `.jar` (via `javap`) showed why: SceneView's `4.x` line
   rewrote `ARScene` around a fully declarative Compose scene-graph (no
   `childNodes` list, `AnchorNode` moved packages) — a real upstream
   change, not a mistake in the code as originally written. Rather than
   rewrite the screen against an unfamiliar API from bytecode signatures
   alone, fetched the real Kotlin source for `arsceneview` `2.2.1` from
   GitHub (tag `v2.2.1`) to confirm it still has the imperative
   `childNodes`/`onSessionUpdated` API the code already targets, then
   pinned to that version instead of the code.

Every fix was verified with a real `./gradlew :app:assembleDebug` — not
assumed — before moving on.

### Error-handling review, and two real bugs it found

Reviewed the AR Activity against a real error-handling checklist rather
than assuming the initial version was complete, and found two genuine
gaps:

- `ARScene`'s `onSessionFailed` callback (fires on a real ARCore session
  failure — camera held by another app, a fatal session exception) was
  never wired up; a session failure would have left the screen silently
  stuck with no way forward. Fixed.
- Tap-to-place model instantiation ran directly inside the gesture
  callback with no error handling; a corrupted or truncated GLB download
  would throw there uncaught, crashing the whole app on tap, not just
  failing that one placement. Fixed — wrapped in a try/catch, and the bad
  cached file is now deleted on failure so "Try again" actually
  re-downloads instead of retrying the same corrupt file forever
  (`downloadToCache`'s dedup-by-URL-hash cache would otherwise have
  served the same broken file back every time).

### Web-side integration

Wrote `web/src/native/arWalkthrough.ts` (the Capacitor plugin bridge —
`isNativeShell()`, `isArWalkthroughSupported()`, `startArWalkthrough()`,
every native call resolving `false`/rejecting cleanly rather than
throwing when not in the native shell) and
`web/src/viewer/ArHandoffButton.tsx` (picks between the new native AR
button and the existing `<model-viewer>` Scene Viewer/Quick Look handoff
— never both, decided once after the async support check resolves).
Wired into `ProjectView.tsx` in place of the old direct `ARHandoff` usage.

### Verification

- Web: `tsc -b` clean, `eslint .` clean (after fixing two real config
  gaps the Capacitor addition had left: `android/` wasn't excluded from
  lint, and `capacitor.config.ts` wasn't in any tsconfig project), all
  166 Vitest tests passing including 5 new ones for the plugin bridge,
  `vite build` clean.
- Android: a full `./gradlew clean :app:assembleDebug :app:testDebugUnitTest`
  passes — including 5 new JUnit tests for `ArScalePreset` (mirroring
  `ScalePreset.test.ts`) replacing Capacitor's placeholder generated test.
- **Not verified**: real ARCore session behavior, plane detection quality,
  tracking, or placement accuracy on an actual device — this sandbox has
  no camera or display, consistent with this project's own repeatedly-
  documented findings about sandbox limitations (see
  [`findings.md`](../findings.md)).

### Delivery

Committed and pushed to PR #2 (already open for this branch). A
debug-signed APK (`com.singhashish.architectar`, minSdk 24, targetSdk 36,
INTERNET + CAMERA permissions, verified with `apksigner`) was built and
committed to `releases/architect-ar-debug.apk` at the repo root — not
part of the app's build/deploy process, added purely so the owner has a
real, clickable link to install and test on their own device. It could
not be delivered as a direct chat attachment (44.8 MiB exceeds the tool's
30 MiB limit); the repo is public, so the raw GitHub URL works without
authentication, confirmed by fetching it back and matching the exact
byte count (46,975,365 bytes).

## What's explicitly not done

- **Print-anchored AR** (image tracking against a printed drawing sheet)
  — the second Phase 4 capability, deliberately deferred, not started.
- **iOS** — Android only.
- **Google Play Store publishing** — needs the owner's own Google Play
  Console account, the $25 registration fee, identity verification, and
  a store listing; none of that is something this session has access to.
  The APK is debug-signed, not release-signed.
- **Real-device AR verification** — everything above is build-verified,
  not hands-on verified. Plane detection, tracking robustness, and
  placement accuracy specifically need a real device test.
