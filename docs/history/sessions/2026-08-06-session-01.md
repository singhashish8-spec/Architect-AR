# Session 1 — 2026-08-06

> Part of [`history/`](../README.md). See [`../findings.md`](../findings.md)
> for the cross-session write-up of this session's key finding, and
> [`../status.md`](../status.md) for current state.

**Starting point.** The product owner reported that the installed app
crashed immediately after accepting the camera permission prompt, even
after updates, and asked for a full bug-finding pass. The app had been
built through Android Studio's Gemini assistant.

**Investigation.** Cloned and read the entire repository. Found:
- `main` contained exactly 2 commits — an IDE-generated "Initial commit"
  and "chore: initialize Android Studio project" — both just the default
  Android Studio **Empty Activity (Compose) template**, renamed to
  ArchitectAR.
- `MainActivity.kt` rendered `Text("Hello Android!")` and nothing else.
- **No camera permission in the manifest, no ARCore, no CameraX, no AR or
  3D code of any kind anywhere in the repo.**
- The README's product description ("Professional Augmented Reality
  toolkit...") didn't match any code present — it described the intended
  product, not anything built.

**Conclusion reported to owner:** the crash could not be reproduced or
diagnosed from this repository, because the app that's pushed to GitHub
never asks for camera access at all. The AR/camera build the owner saw
crash locally in Android Studio was never committed — most likely local,
uncommitted work. See [`../findings.md`](../findings.md) for how this
reframed the whole task.

**Given that, the owner redirected the ask**: rather than chase
undiagnosable local code, build a full roadmap for the product from
scratch, informed by the owner's real-world tools (Revit, SketchUp, Rhino)
and by the sibling **Budget Tracker** project's build pattern (Vite + React
wrapped in Capacitor). Read `Budget-Tracker`'s `README.md` and
`docs/PROJECT_HISTORY.md` for that reference.

## Decisions made this session, in order

1. **Primary use case: client presentation tool** (plus one additional use
   case selected as "Other" during a multi-choice question, whose text
   wasn't captured — still open, see
   [`../../roadmap/decisions.md`](../../roadmap/decisions.md)).
2. **Model pipeline: export-then-import**, not a direct plugin/live-sync
   integration, for Phase 1 — fastest path to a working product, no
   dependency on Autodesk/Trimble/McNeel API access.
3. **Web-first, not native-first** — reversing Budget Tracker's own
   pattern on purpose. Budget Tracker bundles everything into the APK and
   never hosts a live shell, because it bridges to SMS/biometrics and a
   remote shell would dodge Play Store review of that. Architect AR has the
   opposite requirement: a client needs to open a link with zero install,
   so it's hosted live (Vercel/Netlify/Cloudflare Pages), not shipped as an
   APK. Native wrapping returns in Phase 4, once there's a reason that
   needs it (see below).
4. **Viewer stack**: `<model-viewer>` (Google's web component) for the
   one-tap "View in AR" handoff to the phone's built-in AR (Scene
   Viewer/Quick Look) — and separately, **React Three Fiber** for a
   custom-controlled viewer, because element tap-to-inspect needs raycasting
   `<model-viewer>` doesn't expose.
5. **Element data pipeline: IFC, not glTF `extras`.** Plain glTF/GLB export
   strips all of Revit's parameter data. Weighed stuffing custom data into
   glTF's `extras` field (needs a bespoke Revit export script, only carries
   hand-picked fields) against Revit's native IFC export (built-in, no
   plugin, carries the full parameter set) parsed client-side with
   `web-ifc` (open-source WASM IFC parser, the engine behind the former
   IFC.js project). **Chose IFC** — see
   [`../../roadmap/architecture.md`](../../roadmap/architecture.md) and
   [`../../features/element-data-inspection.md`](../../features/element-data-inspection.md)
   for the full reasoning.
6. **Model scale: preset dropdown, not a free slider**, using standard
   architectural drawing scales (1:1 through 1:1000, ISO 5455/RIBA
   convention: 1:1, 1:5, 1:10, 1:20, 1:50, 1:100, 1:200, 1:500, 1:1000),
   chosen once by the architect at import — "everything has to be as per
   architectural standards" (owner's words). Enforced via
   `<model-viewer>`'s `ar-scale="fixed"` in Phase 1. See
   [`../../features/model-scale-presets.md`](../../features/model-scale-presets.md).
7. **Motion-sensor walk-through: Phase 4, not Phase 1.** True physical
   walking through an anchored model (phone motion sensors fused with the
   camera, real 6DOF tracking) needs a custom-built ARCore/ARKit camera
   view, not the OS's handoff AR — deferred to Phase 4's native shell
   rather than pulled forward, keeping Phase 1 to a viewer + AR handoff +
   data panel, no custom native AR code yet.
8. **A structured history file** — requested explicitly by the owner,
   modeled on Budget Tracker's `docs/PROJECT_HISTORY.md`, so any future
   session (human or AI) can pick this project up without re-deriving the
   above.
9. **A third doc set, `docs/engineering/`** — requested by the owner so
   that *any* future AI assistant (not specifically this one) follows the
   same standard for every step, not just the same plan. This pinned the
   remaining open technical decisions to concrete defaults rather than
   leaving them open, specifically so the guide is actually literal enough
   to follow:
   - **TypeScript**, not JavaScript, across the whole stack — a deliberate
     deviation from Budget Tracker's plain JS, justified by this project's
     more complex data shapes (IFC property sets, glTF scene graphs, scale
     enums).
   - **Web app lives in this same repo**, in a new `web/` directory
     alongside the existing `app/` (Android) directory — not a separate
     repo — so the Phase 4 native shell and the web app share one history.
   - **ESLint** (not Budget Tracker's `oxlint`) and **Vitest** (not
     Budget Tracker's `node --test`) — both deviations justified by
     TypeScript-aware linting and native Vite test integration
     respectively.
   - **Supabase (BaaS) + Vercel (hosting)** set as the *default* picks for
     the previously-open "BaaS/hosting provider" decision, so the Phase 0
     build sequence has something concrete to execute — explicitly
     flagged as overridable at Phase 0 kickoff, not a closed decision.
   - A literal, numbered **step-by-step build sequence** for Phase 0 and
     the start of Phase 1, turning the roadmap's bullet-point phases into
     commit-sized, executable steps.
10. **Restructured all three docs into a `docs/` folder hierarchy**
    (`roadmap/`, `history/`, `engineering/`, `features/` + a top-level
    index) instead of three single files — requested by the owner so each
    category stays a manageable size and a new "features" category (one
    spec per feature) has a real home, instead of everything living in
    three ever-growing files. This session file is itself an example of
    the pattern: one file per session under `history/sessions/`, not
    appended to a shared file.
11. **Added a `docs/releases/` category**, one file per shipped version
    (same one-file-per-entry pattern as sessions), plus
    `docs/engineering/release-process.md` defining the versioning scheme
    (semver, MAJOR reserved for a product-owner call on real-client
    readiness), when to cut one, and what it must contain. Explicitly kept
    separate from `history/sessions/`: a session is a unit of *work*, a
    release is a unit of shipped, *versioned product* — not every session
    ships one. No release files exist yet since nothing has been deployed.
12. **Added `.github/PULL_REQUEST_TEMPLATE.md`** with a docs checklist
    (roadmap / session entry / status / engineering / features / release
    note) so the docs discipline in this file is actually checked on every
    PR going forward, not just described.
13. **License: proprietary, all rights reserved.** The repo had no
    `LICENSE` file; asked the owner directly rather than assuming, since
    it's a legal decision, not a technical one. Chosen over open source
    (MIT) because this is a commercial product for the owner's architecture
    business, not a tool meant to be freely reused (including by
    competitors).

## Phase 0 execution

After the docs were in place, the owner asked to proceed with Phase 0
itself — [`docs/engineering/build-sequence.md`](../../engineering/build-sequence.md)
steps 3–11. Executed:

- Scaffolded the Vite + React + TypeScript project into `web/`
  (`npm create vite@latest web -- --template react-ts`).
- **Deviated from the scaffold's default**: current `create-vite` ships
  `oxlint` by default, not ESLint. Removed it and set up ESLint +
  `typescript-eslint` (type-checked rules, including
  `no-floating-promises`) + `eslint-plugin-react-hooks`, per
  [`tech-stack.md`](../../engineering/tech-stack.md)'s pinned choice —
  consistent with, not a new deviation from, what was already decided.
- Installed the rest of the pinned stack: `three`, `@react-three/fiber`,
  `@react-three/drei`, `@google/model-viewer`, `web-ifc` +
  `@thatopen/components`, `@supabase/supabase-js`; dev: Prettier, Vitest +
  React Testing Library + jsdom.
- Hit an npm peer-dependency conflict between `@google/model-viewer`
  (peer `three@^0.183.0`) and the newer `three` that installed by default
  from `@react-three/fiber`'s range — resolved by explicitly pinning
  `three@^0.183.0` to satisfy both, rather than forcing past the conflict
  with `--legacy-peer-deps`.
- Set `"strict": true` in both `tsconfig.app.json` and `tsconfig.node.json`
  (the scaffold didn't set it by default) per
  [`conventions.md`](../../engineering/conventions.md).
- Built the `src/` folder structure from
  [`folder-structure.md`](../../engineering/folder-structure.md)
  (`components/`, `viewer/`, `ifc/`, `pages/`, `services/`, `state/`,
  `types/`, `hooks/`, each currently a `.gitkeep` placeholder).
- Replaced the scaffold's default marketing-page `App.tsx` (Vite/React
  starter content, unrelated assets) with a minimal Phase 0 placeholder,
  and added one real smoke test (`App.test.tsx`) — an empty test suite
  exits non-zero under Vitest, so this was needed to actually prove the
  test pipeline works, not just that it's configured.
- Wrote `.env.example` (Supabase URL/anon key placeholders only, per
  [`environment.md`](../../engineering/environment.md)) and
  `.github/workflows/ci.yml` running lint → typecheck → test → build on
  every PR touching `web/`.
- **Verified all four quality gates pass clean locally**: `npm run lint`,
  `npm run typecheck`, `npm test` (1 passing test), `npm run build`
  (succeeds, ~190KB gzipped to ~60KB).

### What still needs the owner, not an AI

Three Phase 0 items are manual account/settings actions no AI session can
do on its own — they need the repo owner's actual login:

1. **Create a Supabase project** (dashboard) and record its project URL +
   anon key.
2. **Create a Vercel project**, connect it to this GitHub repo, set the
   root directory to `web/`.
3. **Enable GitHub Actions for this repository.** After pushing
   `.github/workflows/ci.yml`, checked whether it actually runs on the PR
   — it doesn't. `GET .../actions/workflows/ci.yml/runs` returns 404, and
   `list_workflows` returns zero, meaning GitHub doesn't recognize the
   workflow file at all (not just "no runs yet" — genuinely not
   registered). This is the signature of Actions being disabled at the
   repo level (Settings → Actions → General → likely set to "Disable
   Actions"), which isn't something the GitHub API/MCP tools available in
   this session can change. **Action needed**: in the repo's GitHub
   Settings → Actions → General, enable Actions (and allow at least
   `actions/checkout` + `actions/setup-node`, the two used here).

Until these happen: the four quality gates (lint/typecheck/test/build)
are verified clean locally, but not yet enforced by CI on GitHub itself,
there is no live preview/production deploy, and Phase 1's build steps
that touch Supabase (schema, upload flow) are blocked. See
[`../status.md`](../status.md).
