### A real CORS gap, found before asking the owner to re-test

Verifying the multipart upload was actually live (via direct API/curl
testing against the real deployment, the same technique
[Session 9](2026-08-14-session-09.md) used throughout) turned up a real
problem before the owner had to hit it: R2's CORS response was missing
`Access-Control-Expose-Headers: ETag`. The part-upload PUT itself
succeeded and R2 did return a real `ETag` header, but without that CORS
directive a browser's `fetch()` reports it as `null` to JavaScript
(browsers only expose a small default set of response headers cross-
origin) — which would have made every real multipart upload fail with a
confusing "missing ETag" error, never actually a CORS-labeled one.
Guided the owner to add `ExposeHeaders: ["ETag"]` to the bucket's CORS
policy; confirmed live via the same preflight-simulation technique
Session 9 used to first diagnose CORS wasn't the problem for the
*previous* failure — this time confirming it genuinely was part of what
would have blocked the *new* multipart path specifically.

## What was built

**One shared progress bar** (`components/PipelineProgressBar.tsx`,
`utils/pipelineProgress.ts`) replacing three separate components
(`ConversionProgressBar`, `FbxConversionStatus`, `UploadProgressBar`).
Real labels per stage ("Reading IFC file…", "Building 3D shapes… (142
of 300 elements)", "Finishing conversion…", "Uploading model… 45.2 MB
of 198.3 MB (23%)"); indeterminate sliding fill for stages with no real
progress data (parsing, FBX loading/exporting) rather than a fabricated
percentage. Required changing `services/r2Service.ts`'s upload progress
callback from a bare `0..1` fraction to real `(loaded, total)` byte
counts, plumbed through `projectService.ts` and `fbxToGlb.ts`.

**One merged file picker** (`components/ModelFileDropzone.tsx`) with
desktop drag-and-drop, replacing the two separate `<input type="file">`
elements every upload form had. A single drop target sorts whatever
files land on it by extension (`.ifc` → the IFC slot, `.glb`/`.gltf`/
`.fbx` → the model slot), so dropping a model file and its IFC data file
together in one drag still fills both slots — the same dual-file
capability the old two-input version had, just one control instead of
two. Used by all four upload sites: `ProjectCreateForm`,
`AdminProjectModels`'s `AddModelForm` and `ModelEditForm`, and
`LocalPreview`. A real side effect: `ModelEditForm`'s "Replace model
file" now accepts FBX too — previously called out in
[`features/fbx-upload.md`](../../features/fbx-upload.md) as deliberately
unsupported, closed here without extra scoping since the merged control
naturally handles it the same way everywhere else.

**Branding header on every page** (`components/BrandingHeader.tsx`),
two variants: a sticky top bar for ordinary pages
(`pages/BoqView.tsx`, `pages/LocalPreview.tsx`) and a small corner-pill
overlay for the full-screen 3D viewer (`pages/ProjectView.tsx`, which
has no header slot to push content down from — matches that page's own
corner-overlay conventions). `BoqView.tsx` kept its own deliberately
non-theme-reactive dark styling (documented reason: matches
`BoqContent.module.css`'s always-dark look) via a `className` override
on the shared component, rather than being forced into the shared bar's
theme-reactive default.

## A real device confirmed the whole pipeline works

Before the CORS/UI work above could even be re-tested, the owner
uploaded a real FBX (native Revit export) through the actual app UI on
their phone — project "NSE," Model 1, shown in the admin dashboard with
a real "Created 15 Aug 2026" date and "1 views" already recorded. This
is the first real confirmation that the whole rebuilt pipeline (Session
9's multipart upload, this session's CORS fix, the new dropzone/progress
UI) actually works end to end on a real device, not just via `curl`.

One real, immediately-useful gap surfaced by that same test: the
"Takeoff" link didn't appear for that model. Not a bug — the Takeoff
link only ever shows for a model with an attached IFC file, and the
owner had only supplied the FBX. Explained the fix (add the IFC file via
the model's own "Edit" form, using the same merged dropzone) rather than
changing any behavior.

## Architecture discussion: how to get everything (data + textures + all disciplines) out of Revit

Prompted by the owner's own question — *"what format that revit can
export contain all the data of model, properties, quantity, material,
etc.?... or tell we can export different multiple files so that they
can get consolidated"* — a long discussion, deliberately kept to
discussion (not code) until the owner asked to build something:

- **No single Revit export format carries everything.** IFC has full
  properties/quantities but only flat-color materials (confirmed:
  Revit's IFC exporter doesn't support texture mapping, though the IFC4
  schema theoretically allows for it). FBX carries real textures but
  minimal structured property data. This app's existing two-file
  approach (FBX for visuals, IFC for data) is the standard answer to
  that gap, not a workaround unique to this app.
- **Real, previously-undocumented gap found while explaining this**:
  tap-to-inspect doesn't actually correlate a separately-exported FBX
  with a separate IFC file — checked directly in the code rather than
  assumed. See [`findings.md`](../findings.md)'s matching entry.
  Quantity Takeoff is unaffected (reads the IFC directly); tap-to-inspect
  on a textured FBX model silently shows no data for every element.
- **The owner clarified they already produce one consolidated NWC per
  project** (all disciplines linked, already used for clash detection),
  which raised: could the app read NWC directly, or go straight from a
  raw Revit file, via Autodesk's own cloud service (Autodesk Platform
  Services, née "Forge")? Researched in real detail (web search against
  Autodesk's own current docs, not memory) — found more risk than
  benefit right now: **no glTF/GLB output for any source format**, only
  Autodesk's own proprietary SVF/SVF2 (needs their own Viewer SDK, not
  this app's three.js pipeline); the one community SVF→GLB bridge is
  archived/unmaintained since March 2026; NWC texture/property fidelity
  through translation unconfirmed; Autodesk's whole developer billing
  model was overhauled in December 2025 with no publicly confirmed
  per-translation price found. **Decided not to pursue** — see
  [`decisions.md`](../../roadmap/decisions.md) for the full research
  writeup.
- **Lumion, also used by the owner, was checked and ruled out** as an
  export source — confirmed directly from Lumion's own support docs
  that it has zero model-export capability of any kind, only rendered
  media (images/video/panoramas). Not relevant to this pipeline at all.
- **A real correction, caught by directly asking**: every doc/code
  comment describing the source of real FBX textures credited
  "Twinmotion-for-Revit." The owner clarified: *"we do not have twin
  motion app"* — their FBX files come from **Revit's own native FBX
  export**, no plugin. Corrected across `decisions.md`,
  `features/fbx-upload.md`, `features/ifc-only-upload.md`, and
  `viewer/fbxToGlb.ts`'s code comment; see
  [`findings.md`](../findings.md) for the full "why this went
  unchecked" writeup.
- **The owner's actual real vision, once asked directly**: a pyRevit
  extension (they already have pyRevit installed) that exports FBX+IFC
  automatically and hands them straight into an embedded browser panel
  showing this app's own upload page — *"nothing manual... every thing
  goes through the pyrevit and web app... making the file lighter...
  easy to navigate... very handy to use."* Talked through the shape
  (WebView2's host-bridge API can hand file bytes to the page without a
  file dialog, so this genuinely needs no changes to this app's own
  code) and two related, smaller ideas that came up alongside it — GLB
  compression (Draco + texture resizing, buildable now, independent of
  the pyRevit project) and real-time multi-user collaboration in the
  viewer (not scoped at all). All three logged as **proposed, not
  built** — see [`decisions.md`](../../roadmap/decisions.md) and
  [`phases.md`](../../roadmap/phases.md) (Phases 5 and 6).
- **A real scope/capability question, answered directly**: the owner
  has a *separate* Claude Desktop session with Revit connected via MCP,
  doing Revit-side work already invisible to this session. Clarified
  plainly: this cloud session cannot see that other session's history,
  has no Revit/MCP connection of its own, and cannot reach the owner's
  PC directly at all (isolated cloud container, no network path to a
  local machine) — any local work needs either a separate local Claude
  Code session run directly on that PC, or manual file handoff. Also
  confirmed: git is **not** required to run Claude Code locally (works
  fine in a plain non-git folder) — relevant since the owner's firm
  doesn't allow git, and that constraint doesn't block a local
  pyRevit-extension project living outside this GitHub repo.

  [`../../roadmap/decisions.md`](../../roadmap/decisions.md) and
