# Session 5 — 2026-08-09

> Part of [`history/`](../README.md). Owner set up their real Supabase
> project (walked through click-by-click), then asked to close out the
> rest of Phase 2: multiple models per project, passcode-protected links,
> and levels/rooms navigation, with branding deliberately moved to last
> since a usable logo file wasn't on hand yet.

## What was done

**Supabase went live.** Walked the owner through creating a real Supabase
project, running `schema.sql`, and wiring `VITE_SUPABASE_URL` /
`VITE_SUPABASE_ANON_KEY` into Vercel's Preview environment. This is the
first session where the app has run against a real backend rather than
`/local`'s no-backend mode.

**Shipped three Phase 2 features**, each with its own feature doc:

1. [Multiple models per project](../features/multiple-models-per-project.md)
   — a `project_models` child table, tab switcher in the viewer.
2. [Passcode-protected links](../features/passcode-protected-links.md) —
   optional project-wide passcode, hashed server-side via a new
   `create_project()` RPC that replaced the old direct anon `INSERT`
   policy on `projects`.
3. [Levels and rooms navigation](../features/levels-and-rooms-navigation.md)
   — a panel listing IFC levels/rooms with a "jump to" camera action.

**A real, live end-to-end test happened this session** — not just unit
tests. The owner uploaded a real project through the actual live app
(not `/local`) and hit a string of real bugs one after another, each
fixed and verified before moving to the next:

- `vercel.json` missing a SPA-fallback rewrite (`/local` 404'd on direct
  navigation) — carried over from finding it late in Session 4, but worth
  noting it's what made *this* session's live testing possible at all.
- `gen_salt(unknown) does not exist` — Supabase installs `pgcrypto` into
  its `extensions` schema, not `public`; the new passcode functions'
  `search_path = public` (a normal `SECURITY DEFINER` precaution) left it
  unreachable. Fixed by adding `extensions` to that search path.
- `column reference "id" is ambiguous` — `get_project()`'s `RETURNS TABLE
  (id uuid, ...)` implicitly declares `id` as a plpgsql variable in scope
  for the whole function body, so a bare `where id = p_id` collided with
  it. Fixed by qualifying it as `projects.id`.
- A generic "Upload failed. Please try again." error hid all of the
  above — fixed by adding `utils/errorMessage.ts`, which surfaces the
  real `.message` off any object-shaped rejection rather than only ones
  that are strictly `instanceof Error`.
- The AR button was rendering a full second copy of the whole 3D model
  in its corner box (that's just how `<model-viewer ar>` works wherever
  it's mounted) — fixed by keeping it mounted off-screen and driving AR
  from a normal button that calls its `activateAR()` method directly.
- Gave the app real visual styling for the first time (it had been raw
  unstyled HTML throughout) — light/dark-aware design tokens and a
  shared card/form stylesheet.

**Multiple models and passcode-protection: built, but not yet re-tested
live** after the pgcrypto/ambiguous-id fixes — the owner's next real
upload attempt should confirm both actually work end-to-end now.

**Levels/rooms navigation: verified against real data before ever
telling the owner to test it.** The first version silently found zero
levels — `web-ifc`'s `getSpatialStructure()` returns IFC type names in
normal mixed case (`IfcBuildingStorey`), not the all-uppercase form its
own type-constant *names* use (`IFCBUILDINGSTOREY`), an assumption that
turned out wrong. Caught this by actually running `web-ifc` directly in
this session's sandbox against the real Duplex sample rather than
trusting the assumption, fixed it, and confirmed via a real Playwright
browser test — loaded the real glTF+IFC pair, opened the panel, saw the
real level/room names (A101–A105, B101–B105, etc.), clicked a room, and
confirmed the camera actually moved to frame that room's real geometry.

## What this changes about the risk picture

Before this session, "does the real upload-and-share flow work end to
end against a live backend" was still an open question — everything
proven so far had been either `/local` (no backend) or a single
successful pass with no real database interaction beyond that first
`get_project()` call. This session answered it the hard way: real usage
surfaced four real, distinct bugs across the database layer, error
handling, and the AR button, each found and fixed in response to an
actual failure the owner hit, not hypothetically. That's a meaningfully
more real signal than a clean first pass would have been.
