## What was done

**Supabase went live.** Walked the owner through creating a real Supabase
project, running `schema.sql`, and wiring `VITE_SUPABASE_URL` /
`VITE_SUPABASE_ANON_KEY` into Vercel's Preview environment. This is the
first session where the app has run against a real backend rather than
`/local`'s no-backend mode.

**Shipped three Phase 2 features**, each with its own feature doc:

1. [Multiple models per project](../features/multiple-models-per-project.md)
   — a `project_models` child table, tab switcher in the viewer.
2. [Passcode-protected links](../features/passcode-protected-links.md) —
   optional project-wide passcode, hashed server-side via a new
   `create_project()` RPC that replaced the old direct anon `INSERT`
   policy on `projects`.
3. [Levels and rooms navigation](../features/levels-and-rooms-navigation.md)
   — a panel listing IFC levels/rooms with a "jump to" camera action.

**A real, live end-to-end test happened this session** — not just unit
tests. The owner uploaded a real project through the actual live app
(not `/local`) and hit a string of real bugs one after another, each
fixed and verified before moving to the next:

- `vercel.json` missing a SPA-fallback rewrite (`/local` 404'd on direct
  navigation) — carried over from finding it late in Session 4, but worth
  noting it's what made *this* session's live testing possible at all.
- `gen_salt(unknown) does not exist` — Supabase installs `pgcrypto` into
  its `extensions` schema, not `public`; the new passcode functions'
  `search_path = public` (a normal `SECURITY DEFINER` precaution) left it
  unreachable. Fixed by adding `extensions` to that search path.
- `column reference "id" is ambiguous` — `get_project()`'s `RETURNS TABLE
  (id uuid, ...)` implicitly declares `id` as a plpgsql variable in scope
  for the whole function body, so a bare `where id = p_id` collided with
  it. Fixed by qualifying it as `projects.id`.
- A generic "Upload failed. Please try again." error hid all of the
  above — fixed by adding `utils/errorMessage.ts`, which surfaces the
  real `.message` off any object-shaped rejection rather than only ones
  that are strictly `instanceof Error`.
- The AR button was rendering a full second copy of the whole 3D model
  in its corner box (that's just how `<model-viewer ar>` works wherever
  it's mounted) — fixed by keeping it mounted off-screen and driving AR
  from a normal button that calls its `activateAR()` method directly.
- Gave the app real visual styling for the first time (it had been raw
  unstyled HTML throughout) — light/dark-aware design tokens and a
  shared card/form stylesheet.

**Multiple models and passcode-protection: built, but not yet re-tested
live** after the pgcrypto/ambiguous-id fixes — the owner's next real
upload attempt should confirm both actually work end-to-end now.

**Levels/rooms navigation: verified against real data before ever
telling the owner to test it.** The first version silently found zero
levels — `web-ifc`'s `getSpatialStructure()` returns IFC type names in
normal mixed case (`IfcBuildingStorey`), not the all-uppercase form its
own type-constant *names* use (`IFCBUILDINGSTOREY`), an assumption that
turned out wrong. Caught this by actually running `web-ifc` directly in
this session's sandbox against the real Duplex sample rather than
trusting the assumption, fixed it, and confirmed via a real Playwright
browser test — loaded the real glTF+IFC pair, opened the panel, saw the
real level/room names (A101–A105, B101–B105, etc.), clicked a room, and
confirmed the camera actually moved to frame that room's real geometry.

## What this changes about the risk picture

Before this session, "does the real upload-and-share flow work end to
end against a live backend" was still an open question — everything
proven so far had been either `/local` (no backend) or a single
successful pass with no real database interaction beyond that first

## Continued: category/discipline visibility, UI rework, lighting

The owner kept testing live and asked for more: category/discipline

Plumbing/Fire/HVAC/etc.), confirmation of whether AR mode can stay

**Confirmed a real technical limit on AR, not a gap to fix**: read
`<model-viewer>`'s own bundled source for exactly what data crosses into
the Scene Viewer/Quick Look AR handoff — only `mode`, `file`, and a few
display flags. No camera position, no room focus, no hidden-category
state. Neither the room-focused camera nor hidden categories can ever
carry into AR mode as things stand; true persistent/filtered AR needs the
custom AR camera view already scoped for Phase 4, not a Phase 2 fix.

**Shipped [category and discipline visibility](../features/category-and-discipline-visibility.md
)** — a second panel next to Levels, grouping every classifiable element
under Architecture/Structure/MEP with per-category show/hide checkboxes.
Verified live against real data, including a real bug: the first version
surfaced IFC bookkeeping entities (`PropertySet`, `RelAggregates`,
`BuildingStorey`) as if they were physical-element categories, because
nearly everything in IFC carries a `GlobalId` via `IfcRoot`, not just
physical elements — fixed by dropping the "Other" fallback bucket
entirely rather than trying to special-case every non-physical type.

**A second production-only bug, more serious than the first**: the owner
reported the categories button missing entirely, even on a brand-new
project — ruling out anything stale. Reproduced by building and serving
the actual production bundle locally (`npm run build` + `npm run
preview`), not just the dev server, and confirmed the same empty panel.
Root cause, confirmed by grepping the built JS directly: production
minification renames `web-ifc`'s dynamically-generated IFC entity
classes, so `line.constructor.name` — which this feature's classification
relied on — returned a meaningless mangled string instead of e.g.
`"IfcWallStandardCase"`. Fixed with a new `getLineTypeName()` helper
(`ifcPropertyLookup.ts`) that reads the type name through `web-ifc`'s
WASM module instead of a JS class identifier, immune to minification —
the same mechanism the levels/rooms feature already happened to use,
which is exactly why *that* feature was never affected by this bug.
**New standing practice going forward**: verify anything
IFC-type-name-dependent against a real production build, not just `npm
run dev`.

**Levels panel reworked twice more** after this, based directly on owner
feedback: "long scroll" → a native `<select>` (technically a dropdown,
but opened as a jarring full-screen picker on Android) → a small anchored
panel matching the category panel's own style. Then, per later feedback,
both panels' top-level entries (each level, each discipline) became
collapsible — closed by default, opened with a small chevron — since a
real building can have a couple dozen rooms or categories once MEP is
involved. The two corner buttons (plus the QR button) were then made
responsive — icon-only on narrow/phone screens, icon+label on wider ones,
matching GitHub's own header button pattern, via a shared
`styles/responsiveLabel.module.css` — after the owner sent screenshots of
the QR and Levels buttons overlapping in portrait mode. Icons were
swapped once more on feedback: a layers icon for Levels, a filter/funnel
icon for Categories.

**Shipped [model lighting](../features/model-lighting.md)** in response
to "why it is not showing a texture of any element...like glass shud show
as a glass". First attempt used drei's built-in HDR preset
(`<Environment preset="apartment" />`), fetched from an external CDN at
runtime — verifying it against a real production build (this session's
own new standing practice) caught a serious problem before it shipped:
the HDR fetch hung indefinitely in a restricted-network test, and because
Environment and the model share one Suspense boundary, that blanked the
*entire* model, not just the lighting. Replaced with a procedural
environment built from `<Lightformer>` panels — plain geometry generated
entirely on-device, no network dependency at all. Re-verified the same
way: confirmed zero external requests, and confirmed a visible
improvement in material realism (shading gradients across walls, a
highlight on the glass parapet) by comparing the same camera framing
before and after.

## Continued: IFC-only upload (no GLB required)

The owner asked a string of questions about getting real Revit materials
into the app, which led somewhere unplanned. Verified (rather than
guessed) that Revit's IFC export never carries real texture images —
confirmed directly via the Autodesk community forums: no BIM standard
body has defined how to represent them, even though IFC4's schema
theoretically has a slot. Checked FBX too, since the owner asked "is
Revit not capable of exporting materials at all" — same gap: Revit's
native FBX export also drops materials by default. The one free
workaround found: Autodesk's own Twinmotion add-in exports FBX *with*
real materials at no cost, which can then go through Blender to a
properly-textured GLB — noted in
[`../roadmap/decisions.md`](../roadmap/decisions.md) for later, not
built yet.

From there, the owner asked to skip requiring a GLB upload entirely and
work from IFC alone. Flagged one hard technical fact before building:
"View in AR" fundamentally needs a real glTF/USDZ file handed to the
phone's AR viewer — confirmed earlier this project from `<model-viewer>`'s
own source — so IFC can't be handed to AR directly no matter what gets
built. Owner chose to auto-convert IFC to a GLB in-app instead of
disabling AR, with a real progress bar (not a fake spinner) since
conversion can take a moment.

**Shipped [IFC-only upload](../features/ifc-only-upload.md)**
(`ifc/ifcToGlb.ts`): `web-ifc` (already used for BIM metadata) can also
load real geometry, not just data — verified every assumption against
the real Duplex sample with a standalone script before writing app code:
the vertex buffer's interleaved position+normal layout, the
transformation matrix's column-major layout, and real per-element RGBA
colors. Generated meshes are named with each element's own real IFC
GlobalId, confirmed by capturing an actual generated GLB's node names in
a real browser test — meaning tap-to-inspect, category hide/show, and
levels/rooms jump-to all keep working completely unchanged, since none of
that code needed to change at all; this feature only changes where the
GLB comes from.

**Another real bug caught before shipping**: `web-ifc`'s own type
declarations claim `FlatMesh.delete()` exists (matching the pattern
`IfcGeometry.delete()` genuinely follows), but calling it threw `s.delete
is not a function` in a real production-build test. Checked directly:
`Object.keys(flatMesh)` on a real object is just `['geometries',
'expressID']` — no `delete` method at runtime, despite the `.d.ts` saying
otherwise. Fixed by simply not calling it. Another instance of this
session's now-repeated lesson: verify against the real running thing,
not what a type declaration or doc claims.

Wired into both `/local` (so it can be tested without a live backend —
which is how it was actually verified this session) and the real upload
form, where the GLB field is now optional and the IFC field's label
explains it becomes required in that case.

## The owner found a real bug in the IFC-only upload feature

Testing the live build, the owner reported: on a project uploaded with
just an IFC file (no GLB), the Levels/rooms and category-hide buttons
appeared but "were not performing" — clicking a room or unchecking a
category did nothing, even though the exact same features worked
correctly on a manually-supplied GLB.

Diagnosed with temporary debug logging against the real Duplex sample
rather than guessing — and found two distinct bugs stacked on each
other, both in how `ifc/ifcToGlb.ts` named the 3D shapes it generates:

1. It named elements with the *compressed* form of their IFC GlobalId,
   but the levels/rooms and category features hand out identifiers in
   the *hyphenated-UUID* form specifically (`invertToHyphenatedGlobalIds()`,
   chosen earlier this project to match an external exporter's own
   convention) — the two never matched, so jump-to-room and
   category-hide silently found nothing every single time.
2. Only the wrapping group (one per element) was named, not its actual
   mesh — but a raycast click always hits the mesh directly, never its
   parent group, so tap-to-inspect read an empty name and also silently
   did nothing.

Both fixed in `ifcToGlb.ts` (convert to the hyphenated form via the
existing `ifcGuid.ts` helpers; name every mesh, not just its wrapping
group) and re-verified against the real Duplex sample with actual
interactions this time — a real click opened a real BIM data panel
("Basic Wall:Exterior - Brick on Block", real IFC properties), a real
room jump visibly reframed the camera, and unchecking "Walls" visibly
removed the walls. Full writeup, including the standing lesson (a node
having *a* name isn't enough to verify — check it's the right *form*,
on the right *object*, via a real interaction) in
[`../features/ifc-only-upload.md`](../features/ifc-only-upload.md).

Also answered two more owner questions about the live build, both
resolved as Vercel project settings rather than app bugs: the shared
link contains "claude-app" because Vercel auto-names preview-deployment
URLs after the git branch (`claude/app-crash-camera-access-y74pyp`), and
a WhatsApp link preview showing "Overview – Vercel" instead of the real
page is very likely Vercel's own Deployment Protection interstitial
blocking the link-preview crawler — confirmed `index.html`'s own
`<title>` is already correctly "Architect AR", ruling out an app-side
cause.

## A follow-on bug from that same fix: the QR card getting covered

Right after the schedule panel fix above shipped, the owner reported
"qr code button is still overlapping..." — a new symptom from the fix
just made. Since the real page needs live Supabase credentials to render
(not available in this sandbox) and the no-backend local-preview page
doesn't have a QR/share feature to test against, confirmed the cause a
different way: built a minimal standalone page reproducing the exact
same CSS rules and DOM order used in the real app, and screenshotted it
before/after.

The cause: `createPortal`'s target is the whole page's root container,
and the portaled schedule panel lands as the *last* child there — after
the QR corner, not before it. With no `z-index` set anywhere, plain DOM
order decided who painted on top, and the schedule panel's dark
background ended up covering the QR share card whenever both were open,
since their footprints spatially overlap (confirmed with a screenshot:
the QR card was almost entirely swallowed by the dark panel behind it).

Fixed by giving every corner control (QR button, Levels/Categories/
Lighting/Search/Schedule row, the AR button, the model switcher) an
explicit `z-index: 2`, and the full-height slide-in panels (Schedule,
ElementDataPanel) `z-index: 1` — controls always paint above content
panels now, regardless of where a portal happens to insert its DOM node.
Re-screenshotted the same reproduction with the fix applied: QR card
fully visible on top. Full writeup in
[`../features/search-and-schedule.md`](../features/search-and-schedule.md).

**Standing lesson, continued**: a `createPortal` fix can silently break
assumptions elsewhere — decoupling a component's visual position from
its DOM position means DOM order (and therefore default paint order) no
longer matches what the JSX implies. Once any portal shares a stacking
context with other absolutely-positioned siblings, those siblings need
explicit `z-index` values rather than relying on JSX order.

### What got built

**Database** (`web/supabase/migrations/008_full_admin_dashboard.sql`,
mirrored into `schema.sql`): a `status` column on `projects` and a
`note` column on `project_models`; a shared `assert_admin()` helper that
every write RPC calls first (raises on a wrong passcode, unlike the
read-side `verify_admin_passcode()` which just returns false); admin-
gated create/update/delete for both projects and models, plus reorder;
and a richer `get_admin_projects()` replacing Phase 2's `get_admin_stats()`
— one call returning each project's full details, models, and view
stats together. The old `create_project()` RPC and the public-facing
"anon can insert project_models" policy are both dropped — creating a
project or model row now requires the admin passcode, not just the anon
key. (Caught and fixed one query bug before shipping: joining
`project_models` and `project_views` directly in the same query would
have cross-joined every model against every view per project, duplicating
entries in the `models` jsonb array — fixed with two separate `left join
lateral` subqueries instead of one flat double join.)

**Frontend**: `services/adminService.ts` (new) wraps every admin RPC,
plus storage-file cleanup (`deleteAdminProject`/`deleteAdminModel` remove
the real files via the Storage API before deleting the database rows —
raw SQL deletes against `storage.objects` don't reliably delete the
underlying file bytes) and duplication (`duplicateAdminProject` copies
the underlying files to fresh Storage paths, not just re-pointing at the
originals, so deleting the source project later can't silently break a
duplicate). `pages/UploadProject.tsx` is gone; its form became
`components/ProjectCreateForm.tsx`, now embedded in `/admin` and calling
the admin-gated creation path. `App.tsx`'s `"/"` route now redirects
straight to `/admin`. `pages/AdminDashboard.tsx` gained search, a status
filter, a sort dropdown, bulk-select-and-delete, and a "Manage" panel per
project (`components/AdminProjectEditor.tsx`) covering details, passcode,
and full model management (add/replace/rename/delete/reorder via move-
up/move-down buttons/note).

## A real bug hiding behind an AR-sounding report

After the second round shipped, the owner pushed back on one answer:
the rotation-pivot issue wasn't about AR mode ("it works ok") — it was
the ordinary in-app 3D preview, before ever tapping "View in AR."
Unlike the AR handoff (a native Scene Viewer/Quick Look app this
project can't reach into at all), the preview is this app's own code
(`viewer/ModelViewer.tsx`, `@react-three/drei`'s `OrbitControls`) —
fully fixable.

Confirmed the cause directly in the code: `<OrbitControls>` was never
given an explicit `target`, so it defaulted to world origin `(0, 0, 0)`.
A Revit export is almost never centered exactly at the origin (real-
world/shared-coordinates survey points routinely put a building
thousands of units away from it), so rotating before ever using "jump
to a level/room" (the one existing feature that already moved
`controls.target`) pivoted around empty space nowhere near the visible
building.

Fixed by auto-framing the camera around the whole model's bounding box
the moment it actually finishes loading — both on first load and when
switching between a project's models — reusing the exact same framing
math the "jump to" feature already had (factored out into a shared
`frameCameraOnBox()` helper rather than duplicated). The trigger needed
its own small `sceneVersion` counter rather than just watching
`modelUrl`: `modelUrl` changes the instant a switch is requested, well
before the new glTF's Suspense boundary has actually resolved, so
keying off it directly would have framed against stale or absent scene
data.

Verified against the real Duplex sample via `/local` (no backend
needed, so no mocking required) in a real production build: the
building now loads centered in frame, and dragging to rotate keeps it
centered and rotating in place instead of swinging toward wherever the
old default pivot happened to sit. All four quality gates passed (73
tests, unchanged — no new tests added for this one, since the fix is
pure WebGL camera math with no existing coverage pattern to extend and
the real verification was the actual rendered rotation). Committed and
pushed to `claude/app-crash-camera-access-y74pyp`.

## The pivot fix shipped with its own regression: a frozen preview

Almost immediately after the pivot fix above went out, the owner
reported the preview screen freezing. Re-read the just-shipped diff
rather than assuming it was unrelated or pre-existing, and found the
cause in the same change: the new auto-frame trigger needed to know
when a *new* scene had genuinely finished loading (not just when
`modelUrl` changed — Suspense means the new GLB isn't ready yet at that
exact moment), so it was driven by a `sceneVersion` counter bumped
inside `onSceneReady`, the callback `Model` already calls once its GLTF
resolves.

That callback had always been written as a fresh inline arrow function
on every `ModelViewer` render — harmless before, since it only wrote to
a ref, and `Model`'s own effect lists it as a dependency. Once it also
called `setSceneVersion(...)`, the fresh identity every render kept
re-firing that effect; each firing bumped the counter; each bump
triggered another render; which produced another fresh arrow function —
a genuine infinite render loop, not just a wasted extra effect run.
Fixed by wrapping `onSceneReady` in `useCallback` with an empty
dependency array, using the functional `setState` update form so
`sceneVersion`'s own current value didn't need to be a dependency
either.

Given the severity (a shipped fix that broke the page entirely) and
that a single screenshot looks identical whether or not a render loop
is pegging the CPU, verification specifically targeted
*responsiveness* rather than appearance: timed `page.evaluate()` calls
immediately after load and again several seconds later (both completed
quickly, not hung), a real UI click on the Lighting toggle (succeeded,
proving the page kept responding to input), and a fresh drag-rotate
confirming the original pivot fix still held. All four quality gates
passed again (73 tests, build). Committed and pushed to
`claude/app-crash-camera-access-y74pyp`.
