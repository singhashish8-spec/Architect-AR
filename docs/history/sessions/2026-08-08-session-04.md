# Session 4 — 2026-08-08

> Part of [`history/`](../README.md). Continuation of Phase 1 verification
> work. Owner asked for an open-source test link after reporting a
> successful AR test using the Khronos `DamagedHelmet.glb` sample — which
> confirmed the AR mechanism works, but (being a generic single mesh with
> no BIM data) told us nothing about the actual open risk: whether
> tap-to-inspect correlation works on a real building.

## What was done

Rather than hand over an unverified link, found and verified a real test
case, then used it to find and fix a genuine bug in the correlation logic
— not a hypothetical one, a concrete one with real evidence.

1. **Found and verified a real Revit-exported IFC sample**: the "Duplex
   Apartment" file from buildingSMART's official community sample set
   (`buildingsmart-community/Community-Sample-Test-Files`), confirmed via
   its own header to be a genuine `Autodesk Revit Architecture 2011`
   export — 2.3MB, real rooms/walls/doors/windows, not a toy asset.
   Verified the download actually works (it's stored via Git LFS; the
   plain `raw.githubusercontent.com` URL only serves the LFS pointer text,
   not the file — `media.githubusercontent.com/media/...` is the URL that
   actually works).
2. **Converted it to glTF using IfcOpenShell** (installed via `pip` in
   this session's sandbox — a real, independent, open-source IFC toolkit,
   not our own code) to get a genuinely paired glTF+IFC test set — 286
   elements, valid glTF 2.0 binary, confirmed by reading the binary
   header directly.
3. **Found a real, concrete bug**: inspected the converted glTF's node
   names and found they're formatted like
   `product-9808fd7f-1a92-405e-9ac9-d59067be1d42-body` — the **expanded,
   hyphenated UUID form** — not the compressed 22-character IFC GlobalId
   form (`2O2Fr$t4X7Zf8NOew3FKau`) that `web-ifc` reads directly and that
   our correlation code was matching against verbatim. **This is exactly
   the failure mode flagged as the single biggest open risk since
   Session 2** — now confirmed concretely, with a real exporter (not a
   hypothetical one), not just a theoretical possibility.
4. **Fixed it properly**: read IfcOpenShell's own reference implementation
   (`ifcopenshell/guid.py`, installed locally, so the actual authoritative
   source — not memory) for the exact compress/expand algorithm between
   IFC's compressed GlobalId and the standard UUID form, and ported it
   faithfully to TypeScript (`ifc/ifcGuid.ts`). Verified the port against
   the real `(compressed, expanded)` pair extracted from the real Duplex
   file via `ifcopenshell.guid` directly — both directions match exactly,
   confirmed before touching any application code.
5. **Updated the correlation index** (`ifc/ifcPropertyLookup.ts`) to index
   every element under all three forms (compressed, bare expanded UUID,
   hyphenated expanded UUID), and added `resolveNodeNameToExpressId()`,
   which tries an exact match first (the original assumption, still valid
   for exporters that use it) and falls back to extracting a UUID-shaped
   substring from the node name (covering IfcOpenShell's
   `product-<uuid>-body` convention, and likely others following the same
   pattern). `useIfcElementData.ts` now calls this instead of a raw map
   lookup.
6. **Tests added**, all using the real verified data, not invented
   fixtures: `ifcGuid.test.ts` (the compress/expand round-trip against the
   real pair), and new cases in `ifcPropertyLookup.test.ts` proving
   `resolveNodeNameToExpressId` matches both naming conventions. 20 tests
   total, up from 14.

## What this changes about the risk picture

**Before this session**: "the glTF-to-IFC correlation is completely
unverified — we don't know if it works." **After**: it's still not proven
to work with whatever exporter the owner ends up actually using — that
still needs a real test — but it's no longer a shot in the dark. We know
concretely that at least one real, commonly-used open-source exporter uses
a different convention than originally assumed, and the code now handles
that convention correctly, proven with a real test case rather than an
invented one. This meaningfully de-risks the single biggest open question
in the project, even though "final answer, yes it works end-to-end" still
requires a real Supabase-backed test with the owner's actual export
pipeline.

## Addendum 2: confirmed working end-to-end, then a real data-quality fix

The owner re-tested `/local` after the routing fix — it worked: uploaded
`Duplex.glb` + `Duplex.ifc`, tapped an element (`M_Upper Cabinet-Double
Door-Wall`), and got a real data panel with `Level`, `Elevation`, and
other genuine IFC properties. **This is the first live confirmation that
this session's correlation fix actually works**, not just unit-tested.

The owner also noticed junk-looking rows like `SerialNumber: SerialNumber`.
Checked the raw IFC file directly with `ifcopenshell` (not guessed):
confirmed this is Revit's own export behavior for unfilled text fields —
see the new finding in
[`findings.md`](../findings.md#finding-revits-own-ifc-export-fills-unset-fields-with-the-fields-own-name-session-4).
Added `hasMeaningfulValue()` to `ifc/ifcPropertyLookup.ts` to filter these
out, with tests against the real observed pattern. 24 tests total now, up
from 20. Pushed as `53961aa`. Owner has not yet re-tested this specific
fix.
