## Closing out the admin dashboard's last two open items

`68bea74` — an **Analytics tab** per project (visit history, a
views-per-day chart, CSV export) and an account-wide **storage usage
tracker** with an owner-editable limit, both flagged as "still open"
since [Session 5](2026-08-09-session-05.md). New
`get_project_view_history()`, `get_storage_usage()`, and
`admin_set_storage_limit()` RPCs, migration 010, mirrored into
`schema.sql`. Full writeup in
[`full-admin-dashboard.md`](../features/full-admin-dashboard.md).

`8cddb93` — **a real bug found the same day**: the Analytics chart's day
buckets didn't line up with what the viewer would actually call "today."
Postgres returns view timestamps in UTC; the chart bucketed each view by
slicing that raw UTC string directly, while separately generating its
own day *labels* from local-midnight `Date` objects — the two disagreed
for any positive UTC-offset timezone (India Standard Time included).
Fixed by deriving both the buckets and the labels from the same
local-calendar-day key instead of mixing a UTC-keyed aggregation with
local-keyed labels.

## The Bill of Quantities: built, reported broken, and a long road to actually fixed

This is the session's real story. Five distinct rounds, each triggered
by the owner actually using the feature against their own real project
— not a sample file — and reporting exactly what they saw.

### Round 1 — building it (`9ece8c6`, `ea6583b`)

Replaced the old count-only Schedule panel with a real, detailed Bill of
Quantities: material and length/area/volume data pulled straight out of
the same IFC file already loaded for tap-to-inspect. The quantity sets
(`Qto_*`) were already being fetched for element inspection but silently
dropped on the floor; materials needed a new `getMaterialsProperties()`
call. Values are unit-converted to metres via the model's own
`IfcUnitAssignment`, since Revit exports commonly use millimetres,
metres, or feet depending on template. Grouped Discipline → Category
with collapsible headers, live search, per-category and per-element
"Locate" (isolate + frame camera), and a CSV export — the bulk
per-element fetch is lazy (only runs once the panel is first opened) and
paced with periodic yields so it doesn't block the main thread on a
large model. A direct "BOQ" link was also added next to each model's
Preview link in the admin Models tab, deep-linking into the 3D viewer
with the BOQ panel pre-opened.

### Round 2 — the owner's own shape for it (`ecc1ec1`)

The owner's own ask, closely paraphrased: *Revit shows length/width/
height/area/volume per element — I want that detected too, and shown
the way Revit would show it: railings in length and height, beams in
length/width/height/volume, doors and windows as counts, walls as area
— every element type shown consistently. Also, clicking BOQ on the
dashboard shouldn't drop me into the 3D preview — it should go straight
to the BOQ.*

Two changes: Width and Height are now pulled out of the IFC quantity
sets as their own dimensions (previously folded into a generic
"length"), and a new `utils/boqQuantityProfiles.ts` gives each category
only the columns that actually matter for it — walls show area, beams
show all four dimensions, doors/windows show a count with no dimension
columns, MEP runs show length. The admin "BOQ" link now opens a
standalone page (`pages/BoqView.tsx`, `/p/:id/boq`) that never touches
the GLB/Three.js pipeline at all — it only needs the model's IFC data,
so it's simpler *and* lighter to load than deep-linking into the viewer
ever was. The tree/search/CSV rendering became a new shared
`components/BoqContent.tsx`, used by both this page and the in-viewer
panel.

A follow-up ask, delivered mid-turn while the above was still being
built: *also categorize by levels.* Handled in the next round.

### Round 3 — level grouping, and the first (incomplete) fix attempt (`237aa35`)

Added a third tier under each category: its own elements broken down by
level, sorted by each level's real bottom-to-top position in the
building (level names like "T/FDN" don't sort correctly as plain
strings).

**The first "not showing values" report arrived here**: *"ok... but it
is not able to calculate and show the values"* — a screenshot showing
every quantity and material column as "—" for a real structural model.
Two changes went out in response: `getPropertySets()` gained a 4th
argument, `includeTypeProperties=true`, to also reach quantities an
exporter had placed on the type object rather than the instance; and
extraction fell back to plain Pset properties (not just proper `Qto_*`
quantity sets) for the known dimension names, since not every exporter
puts dimensional data in a real quantity set. **This was explicitly
flagged in the feature doc as unverified** — no access to the owner's
real file in this environment to confirm against, shipped as "a real,
addressable gap either way," not a confirmed fix.

### Round 4 — the debugging arc: two environment walls, a wrong diagnosis, and how each was actually handled

The owner's report, verbatim: *"i still don't see the values I suggest
you check it yor self..."* — an explicit instruction to self-verify
rather than keep guessing from screenshots. What followed is worth
recording in full, including the parts that didn't work, since the user
asked directly for the failures and how they were treated, not just the
eventual fix.

**Failure 1 — sandboxed browser automation was completely non-functional
in this environment.** Attempted to drive a real headless Chromium
(Playwright, the pre-installed browser at `/opt/pw-browsers/chromium`)
to load the live app and inspect it directly. Every attempt failed with
`net::ERR_CONNECTION_RESET` — tried with and without an explicit proxy
configuration, with `--no-sandbox`/`--disable-dev-shm-usage`, and even
with the sandbox fully disabled at the tool level. Confirmed this was a
hard infrastructure limitation, not a misconfiguration specific to this
app: the exact same failure happened navigating to a completely
unrelated domain (`example.com`), while a plain `curl` through the same
proxy to the same domains worked fine — proving the network path itself
was reachable, and only the browser-launched socket path was blocked.
**How treated**: told the owner directly and honestly that self-checking
this way wasn't possible, rather than continuing to imply the app could
just be inspected directly.

**Failure 2 — the live deployment sat behind a second wall even for
plain HTTP requests.** With browser automation ruled out, tried a direct
authenticated fetch instead. `curl -D -` against the live preview URL
returned a 302 redirect to `vercel.com/sso-api?...` — Vercel's own
per-preview-deployment SSO protection, tied to the account owner's login,
completely unrelated to this app's own Supabase passcode gate. The
owner's offered passcode ("1234") couldn't help here regardless, since
the blocker was one layer up, at the hosting platform, not the
application.

**Response to both**: rather than keep implying "just let me check,"
built a way for the *app itself* to self-report what it was seeing,
directly in its own UI, so a phone screenshot could carry real
diagnostic data instead of just "still blank":

- `193b768` — a collapsed **"Debug info" disclosure** at the top of the
  BOQ page: how many property sets were found on a sampled element,
  every property/quantity name actually present in the raw data (not
  just names this app already recognizes), how many material
  definitions were found, and the raw error text from the fallback
  calls if either had failed.
- The first real screenshot back showed the disclosure landing on a
  **furring wall with zero property sets** — not a bug, a genuinely
  sparse element, but useless for diagnosing the specific wall known
  (via tap-to-inspect, a separate working code path) to have real data.
- `1bbd064` — added a **per-row "Debug" button** on every element
  (`debugBoqElement()` on `useIfcElementData.ts`, reruns the lookup
  fresh for one specific element) so the owner could debug the *exact*
  wall in question, not whichever the app happened to sample first.

**Two more small, real failures surfaced by the owner actually trying
this on their phone**, each fixed the same round:

- `0524c23` — the debug button's 🛈 icon **didn't render at all on a
  real Android device**, showing as a blank box — impossible to tell it
  was even there. Replaced with a plain text label, matching this
  codebase's own existing convention (`Locate`) of text over icon-only
  buttons for exactly this reason.
- A follow-up screenshot showed tapping the (now-visible) button doing
  nothing at all — diagnosed as a **touch-target-size bug**: `padding:
  0` on a small-font text button inside a dense table row gave it a real
  hit area no bigger than the text's own thin bounding box. Fixed with
  generous padding plus a compensating negative margin, so the tap
  target grew without visibly growing the table row. The same
  zero-padding risk existed on the neighboring "Locate" button and got
  the identical fix for consistency.

**A third, separate confusion, resolved by finding the right URL rather
than more debugging**: several rounds of "still not fixed" turned out to
be the owner reloading a **per-commit Vercel preview URL**
(`architect-7d1pjdq29-...`), which is an immutable snapshot that never
updates on new pushes — not a bug report at all, just stale state. Found
the correct, auto-updating **stable branch-alias URL**
(`architect-ar-git-claude-app-9ec6df-...`) via GitHub PR #2's own Vercel
commit status, and gave it to the owner directly.

**The breakthrough, and the corrected diagnosis (`c4c76b3`)**: with the
per-row debug button finally reachable and tappable, a screenshot of
wall `143478` — already proven via tap-to-inspect to carry real Length/
Width/Area/Material data — showed **zero property sets found, zero
materials found, and no error messages at all**. That last part is what
mattered: Round 3's fix had assumed the 4-arg `includeTypeProperties`
call would *throw* if unsupported, with the existing `try/catch`
silently swallowing whatever it threw — but this proved the 4-arg call
was resolving **successfully with an empty array**, no exception
involved, so the catch-based fallback to the proven-working 3-arg call
never engaged at all. The original diagnosis had been wrong in a subtle
but consequential way: "fails" and "succeeds but returns nothing" needed
two different fallback triggers, and the code only had one.
`getPropertySetsWithFallback()`/`getMaterialsPropertiesWithFallback()`
were rewritten to retry the 3-arg call whenever the 4-arg result comes
back **empty**, whether or not it threw — covered by new unit tests for
the "succeeds but empty" case specifically, not just the "throws" case
already covered.

**Confirmed fixed, live, the same day**: wall `143478`'s row showed real
Length/Height/Area/Material values, and the whole model's totals showed
239 elements, 1,927.04 m² total area, 1,412.46 m³ total volume. The
owner's own words: *"it's working..."*

### Round 5 — renamed, redesigned as real schedules, and a formatted Excel export (`8718e48`)

With the underlying data finally confirmed, the owner asked for a
substantial follow-up pass in one message: rename BOQ to "Quantity
Takeoff"; add expand-all/collapse-all; make every category look like a
real detailed architectural schedule with its own dedicated table; add
a per-category toggle for whether it's broken down by level; make the
export mirror whatever that toggle is currently set to; and add a
properly formatted, color-coded, multi-sheet Excel export, "ready to
present as client will be reviewing that."

- **Renamed everywhere user-visible** — corner button, both page titles,
  the passcode-gate submit label, the CSV filename. Internal
  identifiers and the `/boq` URL were deliberately left alone, to avoid
  breaking already-shared links over a purely cosmetic rename.
- **Every category is now its own dedicated schedule table** ("Walls
  Schedule", "Beams Schedule"), with a running "No." index column,
  defaulting to one **flat table with a Level column** — closer to how
  a real Revit schedule actually looks — rather than the previous
  always-grouped-by-level accordion. A new per-category **"Group by
  level" checkbox** switches to the level-banded breakdown for a
  category that spans more than one level.
- **Expand all / Collapse all** added to the toolbar.
- **A formatted, multi-sheet Excel export** via `exceljs` (lazy-loaded —
  `import('exceljs')` only inside the click handler, so its ~75
  dependencies and ~930 KB chunk never load for a visitor who never
  exports anything): a Summary sheet plus one worksheet per category,
  discipline color-coded, with a company/project/model title block,
  frozen header rows, banded rows, and real Excel number formatting. The
  per-category level-grouping toggle carries through into the export,
  so it always matches whatever's currently on screen — not a fixed
  layout.

Full technical detail, including the exact reasoning for every
formatting choice, in [`boq.md`](../features/boq.md).

## Company branding: one dashboard-wide name, not a per-export field (`f43256f`)

Almost immediately after the Excel export shipped, the owner's own
follow-up: *"it's working... but I don't want a separate input for
company... it has to be the same company from my dashboard... also add
a permanent header of company branding on all the page of dashboard and
now and that same reflects on now page and Excel too."*

Removed the local, `localStorage`-backed "Company name" text field the
Excel export had grown on the Quantity Takeoff page, and replaced it
with one account-wide setting:

- `admin_settings` (the existing singleton table already backing the
  admin passcode and storage limit) gained a `company_name` column —
  `web/supabase/migrations/011_company_branding.sql`, mirrored into
  `schema.sql`. Reading it (`get_company_name()`) is deliberately
  public, no passcode — the client-facing Quantity Takeoff page needs to
  show it without asking a visitor to unlock anything, and unlike every
  other column on that table, a company name isn't sensitive. Writing it
  (`admin_set_company_name()`) is passcode-gated like every other admin
  write.
- `AdminLayout.tsx` — which previously rendered no shared chrome above
  its routed pages at all — now wraps every `/admin/*` page in a
  permanent, sticky branding bar, click-to-edit in place.
- The public Quantity Takeoff page and the in-viewer overlay both read
  the same setting via a new read-only `hooks/useCompanyName.ts`, and
  pass it straight through to the Excel export.

**Explicitly still pending**: this needs
`supabase/migrations/011_company_branding.sql` run once in the live
Supabase SQL editor before a real name shows anywhere — flagged directly
to the owner, not yet confirmed live.
