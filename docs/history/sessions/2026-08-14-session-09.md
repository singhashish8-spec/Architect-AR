# Session 9 — 2026-08-14: R2 upload live-debugging arc, mobile upload reliability, background-processing decision

> Part of [`history/`](../README.md). See [`status.md`](../status.md) for
> where things stand right now, and [`findings.md`](../findings.md) for
> the cross-session findings this session produced.

## What happened

The owner finished their Cloudflare R2 setup from
[Session 8](2026-08-12-session-08.md) and tried a real upload. What
followed was a long live-debugging arc against the real deployed app —
three distinct, unrelated failures stacked on top of each other, each
one only visible once the previous one was fixed.

### Failure 1: generic "Failed to fetch" with no detail on which request failed

A real upload attempt surfaced only the browser's own generic "Failed to
fetch" — the same message for offline, a CORS rejection, or a DNS
failure, with no way to tell whether it was this app's own
`/api/r2-upload-url` call or the direct cross-origin PUT to R2 itself.
`src/services/r2Service.ts` gained a `fetchOrThrow(step, ...)` helper
wrapping every fetch with which step it was, turning the next report
into something diagnosable — the owner's next screenshot then read
"**Could not reach this app's own upload-URL endpoint** (network error:
'Failed to fetch')," which named the *first* request (this app's own
same-origin API route) as the one failing. That ruled out R2 CORS as the
cause of *this* specific failure — CORS doesn't apply to a same-origin
request at all.

### Failure 2: Vercel's own Deployment Protection blocking the app's own API route

Direct `curl -D -` testing from this sandbox (something it *can* do,
unlike headless browser automation — see
[`findings.md`](../findings.md)'s Session 7 entry) against
`/api/r2-upload-url` returned `401 {"error":{"message":"Protected
deployment"},"protection":{"vercel_auth_enabled":true}}`. **Vercel's
"Vercel Authentication" (Deployment Protection) was blocking the app's
own API route on this Preview deployment** — not a CORS or code issue at
all.

The owner initially said "it is already turned off," but a re-test still
showed the block. Screenshots revealed why: they'd checked the
**team-level** "Defaults for New Projects" toggle, which only affects
*future* projects, not this already-existing one — the project's own
Deployment Protection setting (a separate page) still showed "Standard
Protection" active. Once found and disabled on the actual project page,
a re-test returned `200` with a real presigned URL — confirmed fixed.

### Failure 3: the R2 access key was still the literal placeholder text

Inspecting that successful `200` response, the presigned URL's
`X-Amz-Credential` parameter read `your_access_key_id_here` — the
example/placeholder text from setup instructions, apparently saved as-is
into `R2_ACCESS_KEY_ID` instead of the real key. The owner reported
editing the env var with the real saved value, then redeploying —
re-tests kept showing the *identical* placeholder, four separate times
in a row, surviving an edit, a save, a redeploy, and even a full
delete-and-recreate of the variable scoped to all three environments.

That many identical failures in a row stopped being explainable as a UI
mistake. **Given a temporary Vercel API token from the owner** (revoked
after use, per their own suggestion when asked to weigh the risk),
direct API inspection of the project's deployment history found the real
cause: **every redeploy the owner triggered had been on `main`
(production target)**, while the URL being tested the whole time was the
`claude/app-crash-camera-access-y74pyp` **branch's own Preview
deployment**, which hadn't been rebuilt since 2026-08-12 — three days
before any of the credential edits. New env var values only take effect
on the next deployment *of that specific branch/environment* — no amount
of re-saving the variable, or redeploying an unrelated branch, was ever
going to reach a deployment that was never rebuilt.

Triggered a fresh deployment of the correct branch directly via the
Vercel API (`POST /v13/deployments` with the existing deployment's
`deploymentId`, redeploying under the `preview` target). Re-tested: real
32-character access key, and a full presign → PUT → GET round trip all
succeeded (`200`, `200`, and the uploaded content read back correctly).

### Failure 4: a real upload from a real (mobile) browser still failed

With the credential fixed and a full curl-based round trip confirmed,
the owner tried a real upload through the actual app UI on their phone.
It failed again — but this time at a *different* step:
"**Could not upload the file directly to storage** (network error:
'Failed to fetch')" — the direct cross-origin PUT to R2, not the app's
own API call. This looked like it could finally be the R2 bucket's CORS
policy, the original hypothesis from Failure 1.

Checked directly: simulated the exact preflight `OPTIONS` request a
browser sends before a cross-origin PUT (`Access-Control-Request-Method:
PUT`, `Access-Control-Request-Headers: content-type`, a real `Origin`
header). R2 responded correctly — `Access-Control-Allow-Origin: *`, PUT
and GET both allowed, `content-type` allowed. **CORS was not the cause.**
This also surfaced a real gap in how Failure 3 had been "confirmed" —
every curl-based PUT test up to that point had validated that the
credentials and signature were correct, but curl doesn't enforce or
preflight CORS the way a browser does, so none of those tests could ever
have caught a CORS problem even if one existed. See
[`findings.md`](../findings.md).

With CORS ruled out, a raw "Failed to fetch" with no HTTP status at all
points at the connection itself dropping mid-transfer — plausible for a
~200 MB file over a mobile connection, especially since the app
currently shows no real progress indicator during the direct PUT (just a
spinner), so there's no way to tell how far it got before dying, and
mobile browsers commonly kill background network activity if the tab
loses focus during a long upload.

## The pivot: resumable upload + a background conversion service

Rather than keep guessing at the mobile failure, the owner proposed a
real architecture change: upload the raw file to R2, let the app detect
and convert it **in the background on a server** (not the client
device), with live progress/ETA on the dashboard, and a catalog UI to
pick a processed file once ready — decoupling "upload finishes" from
"conversion finishes" entirely.

Talked through the shape of it rather than starting to build
immediately, since it's two separable problems of very different size:

1. **Upload reliability** — fixed by switching to R2's chunked/resumable
   multipart upload (retry only the failed piece, not the whole file).
   No new infrastructure needed; this is the actual fix for today's
   mobile failure regardless of what else gets built.
2. **Background conversion service** — a genuinely new piece of
   infrastructure: a persistent worker (not a Vercel serverless
   function — wrong tool for a multi-minute conversion job) polling a
   job queue, running the existing IFC/FBX→GLB conversion logic
   server-side, updating progress/ETA a dashboard can read live. Needs a
   real host; an Oracle Cloud "Always Free" VM was flagged as the
   strongest free fit (always-on, no cold starts) versus Fly.io/Railway-
   style platforms, which mostly aren't free anymore or sleep idle
   workers.

Owner agreed to sequence it: ship the upload-reliability fix first
(fast, unblocks real usage today), scope the background conversion
service as its own follow-up. **Session ended here, on "before
proceeding update all the docs" — the resumable-upload fix itself is not
yet built.**
