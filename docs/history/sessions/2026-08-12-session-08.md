# Session 8 — 2026-08-12: large file storage migration, FBX upload with real textures

> Part of [`history/`](../README.md). See [`status.md`](../status.md) for
> where things stand right now, and [`findings.md`](../findings.md) for
> the cross-session findings this session produced.

## What happened

The owner reported a 169 MB IFC upload failing with "The object exceeded
the maximum allowed size." Checked the live Supabase project's own
Storage dashboard directly rather than guessing at a code fix: Supabase's
Free plan enforces a **fixed, non-configurable 50 MB global upload
limit**, regardless of what any bucket's own `file_size_limit` allows —
this app's `project-files` bucket had always been configured for 500 MB,
which was never the real ceiling. First response suggested a
Supabase-side settings change; the owner pointed out they'd already
stated the 200-300 MB range and a free-tier requirement, which a
Supabase-only fix can't satisfy (Pro removes the cap but isn't free) —
correct pushback, acknowledged, pivoted to Cloudflare R2.

**Migrated new model/IFC uploads to Cloudflare R2** via a presigned-URL
flow: the browser gets a short-lived signed PUT URL from a small Vercel
serverless function (`api/r2-upload-url.ts`) and uploads the file's bytes
directly to R2, never through the function itself — sidesteps Vercel's
own serverless body-size limit entirely, the same class of ceiling this
migration exists to get away from. R2's secret credentials never leave
the server side. Delete and copy (`api/r2-delete.ts`, `api/r2-copy.ts`)
still go through small server-side functions, since the browser has no
safe way to hold R2's secret key.

Full architecture, setup steps, and what's built:
[`features/large-file-storage.md`](../../features/large-file-storage.md).

**Hit a real deploy-time bug getting there**: Vercel's build log showed
`TS2835` errors on the new `api/*.ts` files' relative imports —
compiling under strict Node ESM (`nodenext`) resolution, which requires
explicit `.js` extensions on relative imports even in `.ts` source, since
this repo has `"type": "module"`. `tsconfig.api.json` had been set up
with "bundler" resolution, which doesn't enforce this and let it pass
`npm run typecheck` locally while actually breaking at deploy. Fixed both
the missing extensions and the tsconfig itself (switched to
`nodenext`/`nodenext`), so this class of bug fails locally next time
instead of only showing up in a live build log.

**Then, mid-testing, the owner tried uploading a large file into the
"IFC file" upload slot that turned out to be an `.fbx`** (a Twinmotion-
for-Revit export, selected by mistake) — crashed the WASM IFC parser
with "memory access out of bounds," a completely different binary format
being fed to a parser that can't recognize it. Once found, the owner
asked directly: *"then make it read fbx too,"* followed by *"add a
texture option while uploading fbx... and if turned on... then in
preview mode it should have a toggle to on/off texture."*

**Built FBX upload with real textures/materials** the same session:
every "Model file" input now accepts `.fbx` alongside `.glb`/`.gltf`,
with an "Include textures and materials" checkbox at upload time and a
viewer-side textures on/off toggle shown only for a model that actually
has any. Conversion (`three-stdlib`'s `FBXLoader`/`GLTFExporter`) runs on
the **main thread**, deliberately unlike IFC's own Web Worker-based
conversion — confirmed directly in the installed `three` package's own
source that `TextureLoader` creates a real DOM `<img>` element
(`createElementNS('img')`) to decode textures, which doesn't exist
inside a Worker. A known, accepted tradeoff: a large/texture-heavy FBX
could make the page feel less responsive during conversion, mitigated
with a progress indicator but not eliminated (matches the same class of
issue IFC had before its own Worker move in
[Session 6](2026-08-10-session-06.md)).

Full detail: [`features/fbx-upload.md`](../../features/fbx-upload.md).

**Found and fixed a bundle-size regression before it shipped**: a
production build showed the main JS chunk growing +23 KB gzipped once
`fbxToGlb.ts` (which statically imports `three-stdlib`) got imported
eagerly into three form components. Split the lightweight `isFbxFile()`
check into its own dependency-free file (safe to import everywhere,
synchronously) while every actual conversion call switched to a dynamic
`import('../viewer/fbxToGlb')` at the point of use — confirmed via a
fresh production build that the main bundle returned to its pre-FBX
size, with `fbxToGlb-*.js` as its own separate chunk. Same lazy-loading
pattern already established for `exceljs` in
[`features/boq.md`](../../features/boq.md).
