## Supabase schema written (`web/supabase/schema.sql`)

A `projects` table (id, name, model_url, ifc_url, scale_preset,
created_at) plus RLS. Two deliberate security decisions, not defaults:

- **No permissive `SELECT` policy for `anon`.** A naive `USING (true)`
  policy would let anyone with the public anon key list every project via
  Supabase's auto-generated REST API (`GET /rest/v1/projects` with no
  filter) — RLS can't distinguish "filtered by a known id" from "list
  everything" at the row level. Instead, reads go through a
  `get_project(p_id uuid)` function (`SECURITY DEFINER`, granted to
  `anon`) that only ever returns the one row matching the id the caller
  already provided. This is what actually makes the "unlisted link"
  sharing model (`docs/roadmap/architecture.md#sharing-model`) hold up
  server-side, not just in the UI.
- **`INSERT` is left open to `anon`** — a known, explicitly documented
  Phase 1 gap, not an oversight (same pattern Budget Tracker's
  `docs/PROJECT_HISTORY.md` uses for its own known gaps). There's no
  architect login yet; anyone holding the public anon key could currently
  create junk projects. Must be closed with real auth before any public
  launch. Tracked in
  [`../../roadmap/decisions.md`](../../roadmap/decisions.md).

## Real issues caught by the quality gates (and fixed)

Running `lint`/`typecheck` surfaced genuine problems, not just style
nits — worth recording since they'd bite the next session too if
un-fixed:

- **No `src/vite-env.d.ts`** existed in the Phase 0 scaffold (this
  create-vite version doesn't generate one). Without it, every
  `import.meta.env.VITE_*` access typed as `any`, which cascaded into
  `no-unsafe-assignment` errors in `supabaseClient.ts` and
  `projectService.ts`. Added it with `ImportMetaEnv` properly typed for
  our two env vars.
- **`declare global { namespace JSX }` didn't register `<model-viewer>`**
  as a valid intrinsic element under React 19's `react-jsx` transform —
  needed `declare module 'react' { namespace JSX {...} } }` instead. A
  React 19 typing change, not a mistake in the original approach.
- **Supabase's `.rpc().returns<T>()`** produced a confusing conditional
  type (a "Type mismatch" error type as one branch) without a generated
  `Database` type passed to `createClient()`. Worked around with a single
  explicit cast on the whole response instead of fighting the generic.
- **`eslint-plugin-react-hooks`'s `set-state-in-effect` rule** flagged
  calling `setState` synchronously as the first statement in an effect
  body. Restructured `useIfcElementData`'s effect so every state update
  happens inside the inner async function, not directly in the effect
  callback.

All four quality gates (`lint`, `typecheck`, `test`, `build`) verified
clean locally after these fixes.

## What's built but NOT verified — read before trusting this code end-to-end

This is real, structurally sound code, but large parts of it have never
run against real data, because that's not possible without the Supabase
project and a real device (see Session 1's still-open blockers):

- **The glTF-node-name ↔ IFC-GlobalId correlation** (`ModelViewer.tsx`
  reads the clicked mesh's `.name` and looks it up as a GlobalId) assumes

  the element's GUID in the node name. This has NOT been confirmed against
  a real export — it remains the single riskiest assumption in this

- **The `visualScale()` transform** assumes exported glTF/GLB files are

  real export.

## Addendum: verified the `web-ifc` API calls against the installed package's own source

The proceeding request came with no Vercel/Supabase access, so instead of
stopping, spent the remaining time de-risking the one part of the above
that *could* be checked without live infrastructure: `web-ifc` is already
installed in `node_modules`, so its actual `.d.ts` files, `ifc-schema.d.ts`,
and compiled source were read directly, rather than trusting memory of the
library's API.

**Confirmed correct**, matching what was already written:
- `IfcAPI.properties.getItemProperties(modelID, id, recursive?, inverse?)`
  and `.getPropertySets(modelID, elementID?, recursive?, includeTypeProperties?)`
  signatures match `ifcPropertyLookup.ts`'s calls exactly.
- IFC value types (`IfcLabel`, `IfcGloballyUniqueId`, `IfcIdentifier`, etc.)
  really are wrapped as `{ value, type, name }` objects in the schema —
  confirming `unwrap()`'s approach.
- `IfcRoot.GlobalId: IfcGloballyUniqueId` and `IfcRoot.Name: IfcLabel | null`,
  `IfcPropertySet.HasProperties`, and `IfcPropertySingleValue.{Name,
  NominalValue}` all match the field names `ifcPropertyLookup.ts` reads.

**Found and fixed a real bug**: `loadIfcModel.ts` called
`api.SetWasmPath('/wasm/')` without the `absolute` flag. Reading
`SetWasmPath`'s JSDoc and the actual `locateFileHandler` in
`web-ifc-api.js` confirmed that without `absolute: true`, web-ifc treats
the path as relative to the *executing script's own directory* and
prepends that — silently producing a broken WASM URL in production (where
JS bundles aren't served from the site root). Fixed to
`SetWasmPath(WASM_PATH, true)`, and made the single-threaded-WASM choice
explicit (`Init(undefined, true)`) rather than relying on it being
incidentally selected by the absence of COOP/COEP headers.

**Net effect on confidence**: the `web-ifc` API usage itself is now
verified against the actual installed library, not just "written from
memory" — that risk is substantially reduced. The glTF-node-correlation
risk is unchanged and remains the real open question; nothing short of a
real Revit export resolves it.

## Addendum: closing every gap findable without Supabase/Vercel

Owner asked explicitly to finish anything else that could be finished
before the Supabase/Vercel sign-up. Went back through the Phase 1 code
looking for defects the way the WASM-path bug was found — by reasoning
carefully through what would actually happen at runtime, not just
re-reading for style. Found two more real bugs and fixed both, plus added
real test coverage for the parts that don't need live services.

### Bug: project creation would have failed on every single attempt

`services/projectService.ts`'s `createProject()` called
`.insert({...}).select().single()` to read back the newly created row.
Postgres applies `SELECT` RLS policies to the `RETURNING` clause that
`.select()` triggers — and `schema.sql` deliberately has **no** `SELECT`
policy for `anon` on `projects` (that's what makes "unlisted link" sharing
actually secure server-side, not just in the UI). Net effect: the insert
itself would have succeeded, but the read-back would always return zero
rows, and `.single()` throws on that. **Every upload would have failed at
the last step**, and this would only have surfaced the first time it was
actually tried.

Fixed by generating the project's `id` client-side
(`crypto.randomUUID()`) and skipping `.select()` entirely — the app
already has every field it needs to build the `Project` object without
reading anything back.

### Bug: the file storage bucket was never defined

`schema.sql` created the `projects` table but never created the
`project-files` Storage bucket that `uploadModelFile`/`uploadIfcFile`
upload into, nor any policy allowing `anon` to upload to it. Uploads would
have failed immediately with a permissions error against a fresh Supabase
project. Added: bucket creation (`public = true`, so uploaded files are
readable via their public URL without a separate SELECT policy — that flag
governs the public URL route specifically, it doesn't allow listing the
bucket's contents, so it doesn't reopen the enumeration problem the
`projects` table policy avoids) and an `anon` INSERT policy scoped to that
one bucket. Same known-gap caveat as the `projects` INSERT policy: open to
anyone with the anon key until real auth exists.

### Bug: the data panel would auto-appear on every page load

`pages/ProjectView.tsx` passed `useIfcElementData`'s `loading` (true for
the *entire* time the whole IFC file is parsing in the background, on
every page load) straight into `ElementDataPanel`'s `loading` prop. Net
effect: the data panel would pop up automatically the moment any project
with an IFC file loaded, showing "Loading element data…" — before the
user had tapped anything. Separately, a tap that happened to land *while*
that background parse was still running would silently return no data
(the lookup only checked whether the index was already built, it didn't
wait) rather than resolving once parsing finished.

Fixed by: (1) adding a `readyRef` promise inside `useIfcElementData` that
`getElementDataByGlobalId` now awaits before doing its lookup, so an
early tap correctly waits rather than failing silently; (2) adding a
separate `selecting` state in `ProjectView` that only becomes true once
the user actually taps something, and wiring the panel's `loading` prop
to that instead of the hook's whole-file flag.

### Test coverage added

None of this needs live Supabase/web-ifc to test, since it's pure logic:
- `types/ScalePreset.test.ts` — `isScalePreset`, `scaleRatio`, and
  `visualScale` (the 1/ratio math that's the whole point of the scale

- `ifc/ifcPropertyLookup.test.ts` — `unwrap()`, exported specifically so

- `components/ScalePresetSelect.test.tsx` — confirms the dropdown only

12 tests total (up from 1), all passing, alongside clean

## Addendum 2: local-file preview mode, and a real file-size/format reality check

Conversation with the owner surfaced two things that materially change the
near-term plan, worth recording precisely since they change *why* certain
choices were made, not just *what* was built:

- **Real files are FBX, 200–500 MB each** — not glTF/GLB as assumed
  throughout this project so far, and far larger than anything discussed.
  FBX isn't a web/AR format at all (browsers and phone AR apps can't read
  it) — a glTF/GLB export step is required regardless of hosting choice.
  At 200–500 MB, files also exceed Supabase's free-tier 50 MB per-file cap
  outright (confirmed via Supabase's own docs, not assumed) and would be a
  poor mobile experience even if storage weren't a constraint. Standard
  glTF compression (Draco geometry compression, texture compression) was
  discussed as the fix — expected to shrink files by roughly 80–95%,
  landing well within free-tier limits and reasonable for mobile loading.
  Confirmed with the owner that compression is safe for the BIM data
  specifically *because* the data lives in a separate IFC file untouched
  by glTF compression — the only real caution is avoiding "merge duplicate
  geometry" optimizations, which could break the glTF-node-to-IFC-GlobalId
  correlation this project already flags as its biggest open risk.
- **Considered and partly adopted "load from your own device" instead of
  cloud storage.** Fully local (no Supabase at all) works for in-browser
  viewing and tap-to-inspect, but cannot support "View in AR" — Scene
  Viewer/Quick Look are separate native apps that need a real internet URL
  to fetch the model from; they cannot reach a `blob:` URL local to a
  browser tab. This is a hard platform limitation, not an effort tradeoff.

**Built**: `pages/LocalPreview.tsx` (route `/local`) — pick a glTF/GLB (+
optional IFC) straight from your device via `URL.createObjectURL()`, no
upload, no Supabase, works today. Reuses `ModelViewer`,
`ElementDataPanel`, `ScalePresetSelect`, and `useIfcElementData` as-is —
`loadIfcModel.ts`'s plain `fetch(ifcUrl)` already works against a blob URL
with zero changes needed. Deliberately omits the AR handoff, with an
explanation in the UI of why.

**Also fixed**: `services/supabaseClient.ts` was throwing at *module load
time* if env vars were missing — meaning the entire app failed to load,
including routes like `/local` that never touch Supabase. Changed to a
lazy `getSupabase()` getter that only throws when something actually calls
it, so parts of the app that don't need a backend work standalone.

**Known cost of this addition**: the production JS bundle grew
significantly (Vite flagged it) since every route ships in one bundle,
including Three.js/model-viewer/web-ifc for routes that don't need them.
Logged in
[`../../roadmap/backlog.md`](../../roadmap/backlog.md) as a real
pre-launch task (route-based code-splitting), not silently absorbed.
