## Supabase schema written (`web/supabase/schema.sql`)

A `projects` table (id, name, model_url, ifc_url, scale_preset,
created_at) plus RLS. Two deliberate security decisions, not defaults:

- **No permissive `SELECT` policy for `anon`.** A naive `USING (true)`
  policy would let anyone with the public anon key list every project via
  Supabase's auto-generated REST API (`GET /rest/v1/projects` with no
  filter) — RLS can't distinguish "filtered by a known id" from "list
  everything" at the row level. Instead, reads go through a
  `get_project(p_id uuid)` function (`SECURITY DEFINER`, granted to
  `anon`) that only ever returns the one row matching the id the caller
  already provided. This is what actually makes the "unlisted link"
  sharing model (`docs/roadmap/architecture.md#sharing-model`) hold up
  server-side, not just in the UI.
- **`INSERT` is left open to `anon`** — a known, explicitly documented
  Phase 1 gap, not an oversight (same pattern Budget Tracker's
  `docs/PROJECT_HISTORY.md` uses for its own known gaps). There's no
  architect login yet; anyone holding the public anon key could currently
  create junk projects. Must be closed with real auth before any public
  launch. Tracked in
  [`../../roadmap/decisions.md`](../../roadmap/decisions.md).

## Phase 1 code built

Per `docs/engineering/build-sequence.md` steps 12–19:

- **Types**: `ScalePreset` (the 9 standard presets + a `visualScale()`
  helper), `Project`, `IfcElementData`.
- **`services/projectService.ts`**: upload glTF/GLB + IFC to Supabase
  Storage, create a project row, fetch one by id via `get_project()`.
  Only this module touches Supabase, per
  [`folder-structure.md`](../../engineering/folder-structure.md).
- **`ifc/`**: `loadIfcModel.ts` (loads `web-ifc`'s WASM binary, checked
  into `public/wasm/` as a static asset rather than pulled in via a
  bundler plugin — see the file's own comment for the re-copy-on-upgrade
  caveat), `ifcPropertyLookup.ts` (walks an IFC file's lines once to build
  a GlobalId → expressId index, then reads property sets per element),
  `useIfcElementData.ts` (the React hook tying it together).
- **`viewer/ModelViewer.tsx`**: the React Three Fiber scene — loads the
  glTF, applies `visualScale(scalePreset)` as a uniform transform so a
  1:1000 model actually renders shrunk to tabletop size (not just the
  camera pulled back), wires click/raycasting to read the clicked mesh's
  `name` as its IFC GlobalId.
- **`viewer/ARHandoff.tsx`**: wraps `<model-viewer>`, applying the same
  `visualScale()` via its `scale` attribute plus `ar-scale="fixed"` so the
  AR view and the in-page viewer agree on how big the model looks — an
  earlier draft of this only scaled the R3F camera distance and left the
  model itself unscaled, which would've rendered a 1:1000 master plan at
  literal full building size in the browser. Caught and fixed before
  committing, not after.
- **`pages/UploadProject.tsx`** and **`pages/ProjectView.tsx`**, wired
  into `App.tsx` via `react-router-dom` (`/` and `/p/:projectId`).

## Real issues caught by the quality gates (and fixed)

Running `lint`/`typecheck` surfaced genuine problems, not just style
nits — worth recording since they'd bite the next session too if
un-fixed:

- **No `src/vite-env.d.ts`** existed in the Phase 0 scaffold (this
  create-vite version doesn't generate one). Without it, every
  `import.meta.env.VITE_*` access typed as `any`, which cascaded into
  `no-unsafe-assignment` errors in `supabaseClient.ts` and
  `projectService.ts`. Added it with `ImportMetaEnv` properly typed for
  our two env vars.
- **`declare global { namespace JSX }` didn't register `<model-viewer>`**
  as a valid intrinsic element under React 19's `react-jsx` transform —
  needed `declare module 'react' { namespace JSX {...} } }` instead. A
  React 19 typing change, not a mistake in the original approach.
- **Supabase's `.rpc().returns<T>()`** produced a confusing conditional
  type (a "Type mismatch" error type as one branch) without a generated
  `Database` type passed to `createClient()`. Worked around with a single
  explicit cast on the whole response instead of fighting the generic.
- **`eslint-plugin-react-hooks`'s `set-state-in-effect` rule** flagged
  calling `setState` synchronously as the first statement in an effect
  body. Restructured `useIfcElementData`'s effect so every state update
  happens inside the inner async function, not directly in the effect
  callback.

All four quality gates (`lint`, `typecheck`, `test`, `build`) verified
clean locally after these fixes.

## What's built but NOT verified — read before trusting this code end-to-end

This is real, structurally sound code, but large parts of it have never
run against real data, because that's not possible without the Supabase
project and a real device (see Session 1's still-open blockers):

- **The `web-ifc` API calls** (`loadIfcModel.ts`, `ifcPropertyLookup.ts`)
  are written to the best available knowledge of that library's surface,
  but have never been run against an actual IFC file. `web-ifc` is
  pre-1.0 (`^0.0.77`) and its exact method signatures/return shapes could
  differ from what's written here.
- **The glTF-node-name ↔ IFC-GlobalId correlation** (`ModelViewer.tsx`
  reads the clicked mesh's `.name` and looks it up as a GlobalId) assumes
  whichever Revit-to-glTF exporter the architect actually uses preserves
  the element's GUID in the node name. This has NOT been confirmed against
  a real export — it's the single riskiest assumption in this session's
  work, flagged here so it gets tested first, not last.
- **The `visualScale()` transform** assumes exported glTF/GLB files are
  always authored at true 1:1 real-world units. Also unverified against a
  real export.

**Next concrete step once Supabase exists**: run `schema.sql`, wire real
env vars, and — before anything else — test the upload → view → tap
flow against one real Revit export, specifically to validate the two
assumptions above.
