# Session 6 — 2026-08-10

> Part of [`history/`](../README.md). A day of real-usage polish on the
> viewer's corner panels (four separate bugs found by actually clicking
> around, not spotted in review), a hard fix for a page that looked
> frozen on a real IFC file, and two Phase 3 items scoped into the

## What was done

No single big feature this session — instead, a run of real bugs found
by using the app the way a client actually would (open a panel, close
it, open another, load a real file), each fixed the same day it was
found. All nine commits: `d6be1cc` → `c428c20`.

### The corner panels: four bugs in a row, all from the same underlying pattern

Levels, Categories, Lighting, and Search (later joined by Schedule/BOQ)
each manage a small floating dropdown anchored to a corner button. Four
different symptoms of that shared layout turned out to trace back to
the same handful of root causes:

1. **Opening a panel visibly shoved the other corner buttons to a
   different spot**, snapping back when it closed. Each panel's open
   dropdown was rendered as a plain sibling of its own toggle button
   inside one shared flex row — so its own size pushed everything after
   it in that row. Fixed by anchoring each dropdown with
   `position: absolute` to its own button, taking it out of the shared
   layout flow entirely rather than trying to reserve space for it. See
   [`levels-and-rooms-navigation.md`](../features/levels-and-rooms-navigation.md#addendum-4-opening-any-corner-panel-visibly-shoved-the-other-buttons-around).

2. **More than one panel could be open at once.** Levels, Categories,
   Lighting, Search, and Schedule each tracked their own `open` boolean
   independently, so nothing stopped two (or five) from being open
   together, overlapping on screen. Lifted that state up to one
   "which panel is currently open" value owned by the page itself —
   opening any one now always closes whichever other was open. See
   [`levels-and-rooms-navigation.md`](../features/levels-and-rooms-navigation.md#addendum-5-only-one-corner-panel-open-at-a-time).

3. **Panel text was wrapping onto multiple lines, cramped.** Looked
   like "just needs to be wider," but the real cause was
   `position: absolute` with no explicit width at all — an absolutely
   positioned element shrinks to fit its own content by default, which
   collapsed well below its intended `max-width` and wrapped short
   labels. Fixed with a real explicit width (in `rem`, so it still
   scales with a visitor's own text-size setting), and anchored every
   panel to the shared corner row's own stable right edge instead of
   each panel's individual trigger button — otherwise a wide panel
   triggered from a button that isn't first in the row could run off
   the right edge of the screen. See
   [`levels-and-rooms-navigation.md`](../features/levels-and-rooms-navigation.md#addendum-6-the-menu-text-was-wrapping-and-the-real-cause-wasnt-size).

4. **Some rooms did nothing at all when clicked in the Levels panel.**
   Many rooms in a real IFC export have zero elements as *direct*
   children of their `IfcSpace` — the walls and doors that visually
   bound a room are usually attached to the storey instead, not nested
   under the room itself. "Jump to room" was only ever looking at an
   `IfcSpace`'s own direct children, found nothing for a room shaped
   like that, and silently did nothing — no error, just an
   unresponsive click. Falls back to framing the room's whole level
   when the room itself has no elements to frame. See
   [`levels-and-rooms-navigation.md`](../features/levels-and-rooms-navigation.md#addendum-3-some-rooms-silently-did-nothing-when-clicked).

**A follow-up UX addition the same day**, after using "jump to room" for
real: pivoting the camera correctly lands it centered on the room, but
once you've since moved in closer and want to rotate to look around, the
camera keeps orbiting around that original far-away room-center point —
which feels like swinging around an object rather than turning in place
the way Twinmotion/Lumion's first-person look mode does. Added a small
"look around from here" button that re-anchors the orbit pivot to a
point just in front of the camera's own current position and facing
direction, without changing what "jump to" itself does. See
[`levels-and-rooms-navigation.md`](../features/levels-and-rooms-navigation.md#addendum-7-a-manual-look-around-from-here-control).

### A page that looked frozen on a real IFC file — two real bugs, not one

Uploading a real (not sample) IFC file made the "New project"/"Add
model" page look hung: the progress bar never moved.

**First fix, incomplete**: the IFC-to-GLB geometry loop ran fully
synchronously with no yield back to the browser, so a real building's
worth of elements blocked the main thread long enough that even the
progress bar's own DOM update couldn't repaint. Adding a periodic yield
helped, but `LoadAllGeometry()` itself is one single, opaque,
unyieldable WASM call underneath — no amount of JS-side pacing around it
can keep the page responsive while a real building's worth of geometry
loads *inside* that one call.

**Second fix, the real one**: moved the entire conversion — parsing,
geometry, and glTF export — onto a Web Worker (`ifc/ifcToGlb.worker.ts`)
instead of trying to pace it on the main thread at all.
`convertIfcToGlb()` became a thin wrapper that spins up the worker,
hands it the file's raw bytes as a transferable `ArrayBuffer` (not a
copy), relays `progress` messages back as they arrive, and resolves with
the final GLB (also transferred, not copied). Every existing caller
needed zero changes — same function signature, just running somewhere
the main thread genuinely cannot be blocked by it, no matter how long a
real file takes. Confirmed worker-compatible *before* writing this, not
assumed: `web-ifc`'s own WASM loading uses plain `fetch()` with no DOM
dependency, and the glTF exporter already falls back to
`OffscreenCanvas` when `document` is undefined. See
[`ifc-only-upload.md`](../features/ifc-only-upload.md) for the full
technical writeup.

**A second, unrelated bug hiding behind the same "looks frozen"
symptom**: the admin "Add model" form was silently storing an IFC
file's own URL as if it were the model URL whenever no GLB was
separately given, instead of actually running it through the same
IFC→GLB conversion the "New project" form already did. That produced an
unloadable model with no error message at all — which, from the
outside, looked identical to a frozen page. Fixed alongside the Web
Worker change.

### One more real bug, and a request reversed

**Rendering**: BIM-derived triangulation (Boolean-cut cabinets, joinery
details) doesn't always have fully consistent face winding order, and
materials had defaulted to front-face-only rendering — so some faces
were being silently culled depending on viewing angle, meaning a piece
of geometry could just not be visible from the "wrong" side for no
apparent reason. Switched every IFC-converted material to
double-sided rendering, which makes that entire category of "this piece
just isn't showing up" impossible, at the cost of the (much smaller) GPU
overhead of rendering back faces that would otherwise have been culled.

**A scope reversal, owner's own updated request**: the client-facing
preview page had grown its own "Share" button in an earlier session.
Removed it — sharing now only happens from the admin dashboard's own
Share tab, reversing that earlier decision per the owner directly asking
for it changed.

### Two Phase 3 items scoped, deliberately not built yet

Two roadmap entries added to
[`../roadmap/phases.md`](../roadmap/phases.md) as explicitly scoped-but-
not-built, rather than started half-finished:

- **Free walk/fly navigation** — a Twinmotion-style first-person mode
  (fly/drone first, walk mode on top later), with a mobile
  dual-joystick control scheme, needing an explicit Orbit/Walk/Fly mode
  switcher and an easy way back to orbit.
- **Camera modes, view presets, and a level slicer** — a
  perspective/orthographic toggle, standard Isometric/Plan/Front/Side
  view presets, separate zoom/field-of-view sliders, and a level-driven
  slicer for Revit-style floor plans (distinct from the existing
  "section/clipping planes" idea already on the roadmap).

Both are real, deliberate scope decisions — writing them down now so
they don't get lost, not a signal either is close to being built.

## What this changes about the risk picture

Nothing here was architecturally risky — every fix in this session was a
real, findable, fixable bug in this app's own code (a layout bug, a
missed edge case in room/element relationships, a genuine main-thread-
blocking performance bug), not a technical ceiling or an external
platform limitation. The pattern worth noting for future sessions: four
of today's five corner-panel bugs came from the same "shared flex row +
absolutely/not-absolutely positioned dropdown" shape repeated across
five different panels — worth remembering that a layout bug found in one
panel is worth checking against all the others sharing the same
structure, not just patching the one that was reported.

## What's still pending

- Neither walk/fly navigation nor camera modes/view presets/level
  slicer are built — both are scoped roadmap entries only. See
  [`../roadmap/phases.md`](../roadmap/phases.md).
- The Web Worker move fixes responsiveness but doesn't change how long
  conversion actually takes for a very large building — not yet
  profiled against a genuinely huge real file.
